# Архитектурные принципы

[BRD](BRD.md) задаёт наблюдаемое поведение; [техническая архитектура](technical/README.md) — границы реализации. Комплект обновлён по обратной связи; ручной эталон ожидает предметного согласования.

## Общая идентичность и дерево представлений

Корпоративное пространство имеет одну предметную архитектурную модель. Каталоги систем, компонентов, данных, интерфейсов, отношений, интеграций и решений независимы от проектов. Проект группирует задачи и требования; задача выбирает общий срез и рабочую Git-ветку, не копирует корпоративную архитектуру.

| Уровень | Ответственность |
| --- | --- |
| Объект модели | Устойчивый ID, тип, имя, свойства, происхождение, основания и связи |
| Отношение | Устойчивый ID, типизированные концы и семантика; данные и технический вызов различаются |
| Представление | Срез ссылок на общие ID, назначение/viewpoint, собственные узлы/линии, layout, группировки, локальные подписи и масштаб |
| Дерево | Логическая организация видов: системы, интеграции, потоки, задачи; не единственная огромная диаграмма |
| Задача | Цель, чаты, предложения, затронутые ID, branch/revision и статус работы |

Один сервис доступа в двух видах остаётся одним объектом. Изменение его свойств видно во всех видах; оформление независимых видов сохраняется. Явная локальная подпись вида не меняет имя объекта. По объекту доступны отношения, связанные требования/решения и «где используется». Удаление из вида не удаляет объект; удаление из модели требует разрешения ссылок и проверки влияния. Одноимённые компоненты не склеиваются автоматически.

Это следует из концепций Model Tree / Elements / Relationships / Views / Viewpoints / Properties и Navigator в [официальном руководстве Archi](https://www.archimatetool.com/downloads/archi/Archi%20User%20Guide.pdf). Изучено руководство, практического запуска Archi не было. Не требуется копировать весь его редактор или делать XML основным форматом.

## Формат и проверки

Типизированная предметная модель и независимые валидаторы определяют смысл, JSON — её внутреннее хранение в Git. Схема версионируется; ID устойчивы к переименованию; сериализация детерминирована, несколько файлов дают читаемый diff. Архитектурный YAML не ведётся. Пользователь работает через формы/команды и предложения, а не редактирует JSON для обычных действий. YAML допустим для конфигурации самого приложения.

JSON Schema проверяет структуру; целостность ссылок, допустимость отношений и архитектурные правила проверяются отдельно. Неверный кандидат не заменяет корректную редакцию. Все входы используют одни инварианты. Таблицы и диаграммы строятся из одной ревизии, не становятся вторым источником истины.

ArchiMate задаёт типы и смысл связей, VIEW-01 примера — ограниченный профиль. PlantUML — первый рендерер, .puml и SVG экспортируются из принятой модели без LLM. Направления данных, технических вызовов, ответов и Access read/write не смешиваются. Наличие макроса не доказывает нормативную корректность ArchiMate. Exchange XML и проверка импорта в Archi остаются отдельным открытым решением, двусторонняя синхронизация отложена.

## Git и операционное состояние

Один архитектурный репозиторий на пространство; `main` — согласованная модель, ветка под задачу создаётся от точного актуального main. Принятие предложения человеком разрешает commit в рабочую ветку, но не означает согласования и merge. Постоянной dev нет. Ветка приложения `review/base` имеет другое назначение.

Перед согласованием выполняются формальные проверки, независимый LLM judge, анализ влияния общих элементов и проверка версий источников. Человек согласует точный hash/содержимое/область; merge выполняет уполномоченный человек обычными средствами Git. Система сверяет результат merge с разрешённой ревизией. Новое содержимое или обновившийся main требуют повторных проверок и разрешения. Автоматического разрешения конфликтов нет; GitLab MR не обязательны для MVP.

| Где | Что сохраняется |
| --- | --- |
| Git | Архитектура, дерево видов, существенные подтверждённые решения, проверки, pinned source refs и воспроизводимые исходники схем |
| База приложения | Проекты/задачи, чаты/сообщения, вопросы/ответы, drafts, runs, статусы, настройки, branch/commit references и журнал операций |
| Файловое хранилище | Immutable документы/вложения, крупные бинарные данные и производные экспорты |

История чата — контекст, не реестр подтверждённых решений. Ссылка на источник содержит конкретную версию, hash и локатор; используемые историей версии удерживаются и не заменяются новой загрузкой. Нет общей транзакции трёх хранилищ: контролируемые стадии, operation_id, журнал и восстановление обеспечивают проверяемый результат. Повтор команды не создаёт второе применение; неопределённый исход показывается явно.

Восстановление/revert — новое изменение по текущим правилам, не перенос старого approval. Git не заменяет backup; сохранность всех хранилищ проверяется совместно.

## ИИ, контекст и человек

Анализ BRD, вопросы, проектирование и независимое ревью имеют типизированные результаты. Предложения не меняют модель самостоятельно. Ответы человека — отдельные действия; закрытые вопросы не повторяются без нового основания. Длительное ожидание ответа и сохранённая история переживают restart. Общий механизм структурированной генерации переиспользуется при смене провайдера; формат не доказывает истину.

Каждая роль получает ограниченный релевантный контекст: точные ID/связи, требования, обязательные правила, решения и неизменяемые фрагменты. Весь каталог/чат не отправляются автоматически. Недостающий обязательный контекст нельзя скрыть сокращением; частичное покрытие обозначается. Для структурированных объектов первичны связи, для текста сначала лексический поиск; semantic RAG обосновывается измеренными пропусками. Tool Calling и произвольные действия модели не входят в MVP.

Происхождение хранится для каждого объекта/связи. Оценка выделяет сомнительные **предложения ИИ**, особенно против человека/правил/существующей архитектуры; не нужна шкала и бейдж каждого элемента. Формальный дефект не отменяется judge; недоказанное смысловое замечание не выдаётся за установленное нарушение. Неизвестное обязательное условие остаётся «не проверено» и блокирует итоговое согласование. Исключение допустимо только по правилам источника, не по догадке агента.

Допущение связано с A-01 и риском A-07. Изменение источника/правила инвалидирует зависимые основания и согласования. Метрики Faithfulness/Citation Faithfulness проверяют поддержку утверждений/ссылок, но не полноту источников и архитектурное качество; полнота, корректность и ложные замечания измеряются отдельно на размеченной синтетике.

## Рабочее место и границы

Самостоятельное React-приложение с деревом архитектуры, свойствами, диаграммами и чатом. Несколько чатов в задаче/пространстве, streaming, документы, отмена, ошибки и подтверждение действий человеком входят в MVP. Open WebUI не обязательная зависимость. Готовые React chat components исследованы в [frontend.md](technical/frontend.md); конкретная корпоративная UI-библиотека не объявлена утверждённой.

Light/Dark/System обязательны с сохранением и ручным переключением. Читаемость дерева, таблиц, Markdown, diff и диаграмм проверяется в обеих темах; схемы имеют контрастный фон/палитру, не CSS invert. Поиск, клавиатура, zoom и раскрываемые основания важнее декоративных эффектов.

Модели локальные, LM Studio/vLLM — способы подключения через общий адаптер. Конкретная LLM и смысловые пороги выбираются испытаниями. PDF/DOCX и внешние источники расширяют первую поддержку Markdown/текста после проверки цитируемости. Реальные закрытые данные, конкретная корпоративная эксплуатация и XML-обмен не следуют из синтетического примера автоматически.
