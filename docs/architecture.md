# Архитектурные принципы

[BRD](BRD.md) задаёт наблюдаемое поведение; [техническая архитектура](technical/README.md) — границы реализации. Комплект обновлён по обратной связи; ручной эталон ожидает предметного согласования.

## Общая идентичность и дерево представлений

Корпоративное пространство имеет одну предметную архитектурную модель. Каталоги систем, компонентов, данных, интерфейсов, отношений, интеграций и решений независимы от проектов. Проект группирует задачи и требования; задача выбирает общий срез и рабочую Git-ветку, не копирует корпоративную архитектуру.

| Уровень | Ответственность |
| --- | --- |
| Объект модели | Устойчивый ID, тип, имя, свойства, происхождение, основания и связи |
| Отношение | Устойчивый ID, типизированные концы и семантика; данные и технический вызов различаются |
| Представление | Срез ссылок на общие ID, назначение/viewpoint, собственные узлы/линии, layout, группировки, локальные подписи и масштаб |
| Дерево | Логическая организация видов: системы, интеграции, потоки, задачи; не единственная огромная диаграмма |
| Задача | Цель, чаты, предложения, затронутые ID, branch/revision и статус работы |

Один сервис доступа в двух видах остаётся одним объектом. Изменение его свойств видно во всех видах; оформление независимых видов сохраняется. Явная локальная подпись вида не меняет имя объекта. По объекту доступны отношения, связанные требования/решения и «где используется». Удаление из вида не удаляет объект; удаление из модели требует разрешения ссылок и проверки влияния. Одноимённые компоненты не склеиваются автоматически.

Это следует из концепций Model Tree / Elements / Relationships / Views / Viewpoints / Properties и Navigator в [официальном руководстве Archi](https://www.archimatetool.com/downloads/archi/Archi%20User%20Guide.pdf). Изучено руководство, практического запуска Archi не было. Основные графические операции входят в MVP; полный набор функций редактора Archi отложен.

## Предметная модель и проверки

Независимая предметная модель определяет смысл, допустимые операции и инварианты. Сохранённое представление служит для восстановления её редакции, а не определяет бизнес-логику. Реализация на Python и механизм сериализации закреплены в [технической архитектуре](technical/domain-model.md). Предварительная структурная проверка входа не заменяет предметной валидации.

Неверный кандидат не заменяет корректную редакцию; независимо от источника изменения применяются одинаковые инварианты и архитектурные правила. Таблицы и диаграммы — проекции одной ревизии, а не второй источник истины. После правки общего объекта зависимые проекции обновляются, layout конкретных видов сохраняется.

## Диаграммы и нотация

| Представление | На какие вопросы отвечает |
| --- | --- |
| Потоки данных | Откуда данные поступают, где проверяются, сохраняются, преобразуются и объединяются; как передаются получателю; где читаются и записываются |
| Межсистемные взаимодействия | Какие системы и компоненты участвуют, кто инициирует вызов, какой интерфейс и протокол/защита используются, как вызов связан с потоком данных |

ArchiMate — выбранный язык моделирования элементов/отношений, UML — другой язык с иными назначениями. PlantUML — средство описания и генерации диаграмм, а React-библиотека интерактивного редактора — решение frontend. Замена ArchiMate на UML требует отдельного архитектурного решения.

VIEW-01 примера задаёт ограниченный профиль: допустимые типы элементов/отношений и смысл направлений. Движение данных, инициатор технического вызова, ответ и Access read/write хранятся раздельно. Наличие макроса не доказывает нормативную корректность ArchiMate. Проверенный срез и версия профиля/рендерера воспроизводимо дают редактируемые .puml и SVG без LLM. Экспорт не меняет общие ID. Ошибка рендера оставляет прежний экспорт с явной старой ревизией.

Exchange XML и практическая проверка импорта в Archi — отдельное открытое решение; двусторонняя синхронизация отложена.

## Git и операционное состояние

Один архитектурный репозиторий на пространство; `main` — согласованная модель, ветка под задачу создаётся от точного актуального main. Принятие предложения человеком разрешает commit в рабочую ветку, но не означает согласования и merge. Постоянной dev нет. Ветка приложения `review/base` имеет другое назначение.

Перед согласованием выполняются формальные проверки, независимый LLM judge, анализ влияния общих элементов и проверка версий источников. Человек согласует точный hash/содержимое/область; merge выполняет уполномоченный человек обычными средствами Git. Система сверяет результат merge с разрешённой ревизией. Новое содержимое или обновившийся main требуют повторных проверок и разрешения. Автоматического разрешения конфликтов нет; GitLab MR не обязательны для MVP.

| Где | Что сохраняется |
| --- | --- |
| Git | Архитектура, дерево видов, существенные подтверждённые решения, проверки, pinned source refs и воспроизводимые исходники схем |
| База приложения | Проекты/задачи, чаты/сообщения, вопросы/ответы, drafts, runs, статусы, настройки, branch/commit references и журнал операций |
| Файловое хранилище | Immutable документы/вложения, крупные бинарные данные и производные экспорты |

История чата — контекст, не реестр подтверждённых решений. Ссылка на источник содержит конкретную версию, hash и локатор; используемые историей версии удерживаются и не заменяются новой загрузкой. Нет общей транзакции трёх хранилищ: контролируемые стадии, operation_id, журнал и восстановление обеспечивают проверяемый результат. Повтор команды не создаёт второе применение; неопределённый исход показывается явно.

Восстановление/revert — новое изменение по текущим правилам, не перенос старого approval. Git не заменяет backup; сохранность всех хранилищ проверяется совместно.

## ИИ, контекст и человек

Извлечение требований из описаний заказчика, ТЗ, BRD и других материалов, вопросы, проектирование и независимое ревью имеют типизированные результаты. Предложения не меняют модель самостоятельно. Ответы человека — отдельные действия; закрытые вопросы не повторяются без нового основания. Длительное ожидание ответа и сохранённая история переживают restart. Общий механизм структурированной генерации переиспользуется при смене провайдера; формат не доказывает истину.

Каждая роль получает ограниченный релевантный контекст: точные ID/связи, требования, обязательные правила, решения и неизменяемые фрагменты. Весь каталог/чат не отправляются автоматически. Недостающий обязательный контекст нельзя скрыть сокращением; частичное покрытие обозначается. Для структурированных объектов первичны связи, для текста сначала лексический поиск; semantic RAG обосновывается измеренными пропусками. Tool Calling и произвольные действия модели не входят в MVP.

Происхождение хранится для каждого объекта/связи. Оценка выделяет сомнительные **предложения ИИ**, особенно против человека/правил/существующей архитектуры; не нужна шкала и бейдж каждого элемента. Формальный дефект не отменяется judge; недоказанное смысловое замечание не выдаётся за установленное нарушение. Неизвестное обязательное условие даёт результат проверки «не проверено» и статус контроля «Недостаточно данных», блокируя итоговое согласование. Происхождение, четыре статуса контроля по FR-09 и human approval независимы; «Подтверждено» проверками не означает решения архитектора. Исключение допустимо только по правилам источника, не по догадке агента.

Допущение связано с A-01 и риском A-07. Изменение источника/правила инвалидирует зависимые основания и согласования. Метрики Faithfulness/Citation Faithfulness проверяют поддержку утверждений/ссылок, но не полноту источников и архитектурное качество; полнота, корректность и ложные замечания измеряются отдельно на размеченной синтетике.

## Рабочее место и границы

Графический веб-интерфейс с деревом архитектуры, свойствами, диаграммами и чатом. Архитектор преимущественно работает с графическим представлением: выбирает объект/отношение, редактирует свойства, добавляет/изменяет связи, переходит к связанным видам и всем использованиям общего элемента. Сравнение редакций и предложения ИИ показываются непосредственно в контексте модели; применить/отклонить — отдельное решение человека. Расположение элементов независимо для каждого вида. Это основные операции MVP в пределах согласованного профиля, а не обещание полного редактора Archi.

Несколько чатов в задаче/пространстве, потоковые ответы, документы, отмена, ошибки и подтверждение действий человеком входят в MVP. Конкретные компоненты описаны в [техническом frontend](technical/frontend.md).
Light/Dark/System обязательны с сохранением и ручным переключением. Читаемость дерева, таблиц, Markdown, diff и диаграмм проверяется в обеих темах; схемы имеют контрастный фон/палитру, не CSS invert. Поиск, клавиатура, zoom и раскрываемые основания важнее декоративных эффектов.

Модели локальные, подключение изолировано общим адаптером. Конкретная LLM и смысловые пороги выбираются испытаниями. PDF/DOCX и внешние источники расширяют первую поддержку Markdown/текста после проверки цитируемости. Реальные закрытые данные, конкретная корпоративная эксплуатация и XML-обмен не следуют из синтетического примера автоматически.
