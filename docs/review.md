# Согласование требований и приёмка

Документация актуализирована по обратной связи; это не имитация предметного утверждения ручного эталона.

## Зафиксированные решения и открытые вопросы

| ID | Состояние | Решение или оставшийся вопрос |
| --- | --- | --- |
| Q-01 | Открыт предметный review полного комплекта | Проверить полноту обновлённого MVP и ручного эталона A-01–A-07; библиотеки не заменяют приёмку поведения |
| Q-02 | Основной подход определён; детали UX открыты | Отдельный React UI, общая модель/дерево, чат, файлы, Light/Dark/System. Окончательная UI-библиотека и расположение панелей не утверждены |
| Q-03 | Открыт | Нужен ли обязательный обмен с Archi при первой приёмке? Только при положительном решении включить XML и реальный import test; .puml/SVG не выдавать за обмен моделью |
| Q-04 | Прежний вопрос о YAML снят | A-06 переопределён как структурированная JSON-модель. Достаточность её предметного состава проверяется на обновлённом примере, YAML не параллельная модель |
| Q-05 | Открыт | Политика сроков хранения source versions, удаления веток, backup и прав на обычный Git merge; используемые источники нельзя удалять до определения retention |

Общая корпоративная модель, ветки под задачи от main, PostgreSQL/Git/files, отказ от обязательного архитектурного YAML и локальные LLM заданы для текущего проектирования. MUI/assistant-ui/Instructor — обоснованные технические рекомендации, не решения заказчика о корпоративных продуктах. Конкретные модели/capabilities и числовые цели смыслового качества проверяются экспериментально. Реальные закрытые данные и требования Альфа-Банка этим комплектом не вводятся.

## Ручной эталон и что проверить

Вводные — [синтетический BRD](examples/reporting-system.md), результат — [A-01–A-07](examples/reporting-system/expected-result.md), данные — [model.json](examples/reporting-system/model.json). Для внешнего review достаточно [BRD PDF](pdf/brd.pdf) и [примера PDF](pdf/example.pdf); второй включает вводные, таблицы, обе диаграммы и полную JSON-модель. Согласование и ответы человека не имитируются.

Проверить сохранность систем, данных, потоков, интерфейсов, ограничений SEC-01–SEC-08, источников и шести решений прежнего примера. Один corporate access component должен использоваться двумя представлениями с одним ID; свойства общие, layout различен. Бизнес-прокси остаётся в каталоге вне используемого среза. Ветка задачи изменяет общую модель; не создаётся repo отчётности как отдельная корпоративная архитектура.

В примере дневные продажи идут через готовый Kafka, справочник — по расписанию, обработка выделена из пользовательского сервиса. Требования к 2FA/прокси/сквозному TLS относятся к проектируемой отчётности. Физические эксплуатационные показатели и доставка не испытаны. Архитектурные предложения ручного автора остаются предложенными, без вымышленных AI scores/approval.

## Условия начала реализации

Согласовать конкретную редакцию требований и предметный результат примера. Технические решения и короткий [план](technical/implementation-plan.md) уже подготовлены; не требуется новая серия проектных PR перед первым работающим сценарием. Поддерживаемые входные форматы сверх первого Markdown/текста и обязательность Archi уточняются по практической необходимости.

Слияние документационного PR не является утверждением всех предложенных решений. Решение архитектора относится к конкретному содержимому/commit. `review/base` — ветка приложения; `main` в будущей системе — согласованная архитектура корпоративного пространства.
