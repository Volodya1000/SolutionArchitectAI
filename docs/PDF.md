# Редактируемые документы и PDF

В репозитории хранятся две готовые PDF-версии и их редактируемые исходники LaTeX:

| Документ | PDF | LaTeX |
| --- | --- | --- |
| Бизнес-требования MVP | [brd.pdf](pdf/brd.pdf) | [brd.tex](latex/brd.tex) |
| Сквозной пример системы отчётности | [example.pdf](pdf/example.pdf) | [example.tex](latex/example.tex) |

Второй документ включает исходный BRD, ожидаемый архитектурный результат, обе диаграммы и **полную** JSON-модель. Для чтения PDF другие файлы не требуются. Текст доступен для поиска и копирования; диаграммы сохраняются в векторном виде.

## Правки и сборка

Редактируйте `docs/latex/brd.tex` и `docs/latex/example.tex` напрямую. Общие шрифты, цвета, поля и оформление находятся в [common.tex](latex/common.tex). Затем из корня репозитория выполните:

```sh
python3 scripts/build_documents.py
```

Обычная сборка **не перезаписывает LaTeX** и сохраняет ручные правки. Перед изменениями этой редакции повторная генерация исходных LaTeX дала нулевой diff: отдельных ручных правок не обнаружено; общий `common.tex` сохранён. Сборка преобразует актуальные SVG-диаграммы во временные PDF, читает `model.json` и все перечисленные в нём JSON-файлы, проверяет SHA-256/размер закреплённых источников, формирует временное приложение и подключает его целиком и компилирует каждый документ дважды. Результат сохраняется в `docs/pdf/`; временные файлы и журналы — в игнорируемом `.build/documents/`. Ошибки компиляции, отсутствующие символы и выход текста за поля останавливают сборку.

Markdown остаётся самостоятельной редактируемой версией документации. Синхронизация текста Markdown и LaTeX выполняется явно. Если после изменения Markdown нужно заново получить LaTeX, выполните:

```sh
python3 scripts/build_documents.py --refresh-tex
```

**Эта команда перезаписывает `brd.tex` и `example.tex`, включая ручные правки в них.** `common.tex` сохраняется. Перед обновлением сохраните нужные правки в Git и проверьте полученный diff. В этой редакции текст не скрывается по старым жёстко заданным фразам: вводные, ограничения и статус эталона публикуются из Markdown. Источники регенерации: `docs/BRD.md`, `docs/examples/reporting-system.md` и `docs/examples/reporting-system/expected-result.md`. Относительные ссылки превращаются в понятные подписи; диаграммы и JSON включаются в документ. Генератор измеряет заголовок каждой таблицы вместе с первой строкой данных и резервирует необходимую высоту; непосредственно предшествующий заголовок раздела переносится вместе с ними. Остальные строки многостраничных таблиц свободно переносятся с повторением шапки. Общая типографика удерживает заголовки разделов со следующим содержимым. Эти правила действуют и после повторного `--refresh-tex`, без ручных разрывов страниц или удержания таблиц целиком.

Перед сборкой после изменения `.puml` пересоздайте обе SVG из исходников. Для текущего комплекта использован PlantUML 1.2026.9 и Graphviz; например, с локальным JAR:

```sh
java -Djava.awt.headless=true -jar /path/to/plantuml-1.2026.9.jar -charset UTF-8 -tsvg docs/examples/reporting-system/data-flow.puml docs/examples/reporting-system/interactions.puml
python3 scripts/build_documents.py --refresh-tex
```

Обычная PDF-сборка использует сохранённые SVG и сама не запускает PlantUML. После пересборки проверьте таблицы, переносы и обе диаграммы визуально; экспорт кода `.puml` обязателен для A-03 (диаграмма потоков данных) и A-05 (диаграмма межсистемных взаимодействий).

## Инструменты

Нужны Python 3, XeLaTeX, Inkscape и шрифты DejaVu с поддержкой кириллицы. Pandoc требуется только для `--refresh-tex`.

Для Ubuntu/Debian:

```sh
sudo apt-get update
sudo apt-get install -y texlive-xetex texlive-latex-extra texlive-lang-cyrillic texlive-fonts-recommended fonts-dejavu inkscape
# Только для регенерации LaTeX из Markdown:
sudo apt-get install -y pandoc
```

Для временных меток используется `SOURCE_DATE_EPOCH`, а если он не задан — время последнего коммита, изменившего исходники сборки (без `docs/pdf/`). Это уменьшает лишние изменения PDF при одинаковых исходниках и версиях инструментов. Побайтовая идентичность между разными версиями TeX, шрифтов и Inkscape не гарантируется.

## Автоматическая сборка

[GitHub Actions](../.github/workflows/build-pdf.yml) компилирует существующие LaTeX-исходники и публикует оба PDF как артефакт запуска. Регенерация из Markdown в CI не выполняется, поэтому ручные правки LaTeX сохраняются.

Workflow выполняет сборку и загружает артефакты без записи в Git. Обновлённые PDF включаются в тот же проверенный коммит, что и исходники; сборка не создаёт дополнительных коммитов в ветке PR. Одновременные сборки одного PR отменяют устаревшие запуски.

## Проверки издателя и JSON-приложения

```sh
python3 -m unittest discover -s scripts -p 'test_*.py'
```

Четыре regression-теста проверяют включение всех JSON-файлов без потери значений, отклонение duplicate keys, неизвестной schema_version и изменённого pinned source. Это тесты генератора документов, не backend будущего приложения. CI выполняет их перед сборкой. Полная предметная валидация/JSON Schema не выдаётся за выполненную этим издательским helper: `model.schema.json` описывает форму примера, ссылки проверяются отдельно при подготовке комплекта.

JSON-приложение строится в `.build/documents/json/`; запись имеет отступы и допускает построчные переносы страниц, все значения включены. Схема — отдельный исходник репозитория, данные всех восьми файлов приведены в PDF целиком. Обычная сборка не меняет LaTeX и не требует Pandoc; `--refresh-tex` нужен только после изменения Markdown. После обновления исходного документа нужно явно обновить source version/hash/size, иначе сборка останавливается. Это предотвращает публикацию новой версии под старой ссылкой.

Для визуальной проверки можно использовать `pdftoppm -scale-to 1400 -png docs/pdf/brd.pdf .build/documents/brd` и аналогично для example. Проверяются все страницы, переносы/повтор шапок, кириллица, обе диаграммы и JSON-приложение; успешная компиляция сама по себе не подтверждает читаемость.
