# Отдельные проверочные сценарии будущего MVP

Основной [синтетический BRD](examples/reporting-system.md) содержит полные вводные. Сценарии ниже выполняются на отдельных проверочных копиях и не входят в PDF основного примера. Это план проверок, а не результаты испытаний готового продукта.

## Неполные и противоречивые вводные

| Изменение проверочной копии | Ожидаемое поведение |
| --- | --- |
| Удалить из R-01 условия действия минутной задержки при паузе по R-06 | Агент LLM as judge замечает возможное противоречие; система запрашивает условия SLA и восстановления, не исправляя требование самостоятельно |
| Удалить из R-03 правила очистки, повторной доставки и работы с резервными копиями | Система запрашивает границы и порядок хранения; не выдаёт выбранную ИИ политику за исходное требование |
| Удалить из R-04 допустимый диапазон дат и поведение за его пределами | Система запрашивает недостающие условия; не ограничивает диапазон молча |
| Принять явное допущение вместо ответа | В A-01 (реестр требований и уточнений) создаётся запись «Подлежит верификации» с владельцем и условием проверки, в A-07 (реестр решений и отчёт проверок) — связанный риск. Допущение не отменяет обязательные правила |

До ответа или допустимого принятого допущения зависимое проектирование при блокирующем вопросе остановлено. Непроверенные обязательные условия не позволяют завершить согласование. Возможные смысловые замечания требуют проверки человеком; качество их обнаружения измеряется по AC-15.

## Изменения и отрицательные сценарии

| Проверка | Изменение проверочной копии | Ожидаемое поведение |
| --- | --- | --- |
| Смена стандартов | Для отдельно подготовленной ранее согласованной модели с HTTP ввести обязательный HTTPS | Формальный валидатор указывает связь и новую редакцию правила; согласование зависимых результатов теряет актуальность, новое утверждение блокируется |
| SEC-05 | Убрать подтверждение второго фактора из сессии | Доступ отклоняется; нарушение блокирует согласование |
| SEC-06 | Направить внешний обмен в обход прокси | Блокирующее нарушение по конкретному маршруту |
| SEC-07 | Изменить профиль на клиентское обслуживание 24/7, оставив технологический прокси | Блокирующее нарушение до выбора отказоустойчивого бизнес-прокси |
| SEC-08 | Убрать обязательное шифрование и разрешённый защищённый канал, сохранив маршрут через прокси | Блокирующее нарушение с указанием потока и отсутствующей защиты |

Смысловой контроль не отменяет формальную блокировку. Прежний согласованный снимок остаётся доступен.

## История Git — FR-11, AC-17

Проверяются черновики без замены корректной модели, commit каждого принятого изменения в task branch, автор/время/причина и diff JSON/.puml. Коммит не означает approval. Две задачи стартуют от точного main и используют один корпоративный компонент. Принятое изменение не попадает в main без разрешённого human merge. Смена main и conflict общих объектов требуют явного обновления ветки, новых checks и approval; сложного auto-resolution нет. Разрешённые hash/tree/область сверяются с фактическим merge. Старое согласование не переносится при восстановлении; создаётся новое изменение. Сбой до/после Git ref update и потеря HTTP-ответа не создают дублей при повторе operation_id, неизвестный исход виден пользователю.

## Общие объекты и дерево — FR-06/08, AC-16

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Открыть сервис корпоративного доступа из двух видов | Один object ID и свойства, собственные visual node IDs/layout/labels; where-used показывает оба вида |

| Повредить JSON, duplicate key, неизвестная schema version или reference | Последняя корректная редакция сохранена, поле/причина ошибки доступны; это отдельные проверки эталона; в будущем UI и LLM проходят одинаковые предметные проверки |
| Каталог содержит бизнес-прокси вне рабочего среза | Не создаётся ложный isolated-node defect |

## Чаты, вопросы и источники — FR-02/12, AC-18

Два чата одной задачи и чат пространства сохраняют историю отдельно. Streaming/отмена/ошибка/частичный ответ не перемешиваются при переключении. Restart в waiting_input восстанавливает вопрос; ответ человека учитывается, закрытый вопрос не генерируется заново без основания. Предположение ИИ не становится ответом. Поздний proposal к старой ревизии остаётся черновиком. Недоступный judge не выдаёт успешного согласования.

Новая загрузка создаёт file/version/hash; source pin ссылается на прежнюю immutable версию. Попытка удалить referenced source запрещена; сбой между upload, journal, commit и SQL completion восстанавливается без подмены документа. Повреждение hash/недоступность источника видны; incomplete export не объявляется текущим. История сообщений не заменяет существенное решение в модели.

Проверить переполнение контекста и исключённый релевантный запрет: обязательные правила не отбрасываются молча, partial review не считается полным. Faithfulness и Citation Faithfulness дополняются source coverage, полнотой генерации/нарушений и долей ложных замечаний.

## Темы и длительная работа — FR-13, AC-19

Проверить Light/Dark/System, ручной override, reload и смену системной темы. В обоих режимах читаемы дерево/поиск, свойства/связи, длинные русские таблицы, обе SVG, Markdown/code blocks, diff, ошибки и модальные окна. Основные действия доступны с клавиатуры, diagram zoom не обрезает подписи. Сомнительные предложения ИИ компактны, подробности/источники раскрываются; оценки не загромождают каждый объект.

## Контроль качества и графический review — FR-06/09, AC-09/11/16

Проверить четыре статуса и приоритет: доказанное нарушение перекрывает недостаток данных и требует исправления; отсутствие обязательных сведений блокирует согласование; доступные, но непроверенные основания дают «Требует проверки»; только все актуальные обязательные проверки позволяют «Подтверждено». Успешный контроль предложения ИИ не меняет происхождение и не выдаёт human approval. Текст пояснения не принимается как значение формализованного статуса. На экране выделяются наиболее важные ситуации, подробности раскрываются.

В будущем интерфейсе: выбрать узел/отношение, изменить свойства/разрешённую связь, перейти к связанному виду, найти все использования, сравнить изменения, применить/отклонить предложение в контексте. Layout двух видов независим. В текущем PR CI проверяет сохранённый эталон и проекции; эти интерактивные сценарии не объявляются реализованными.
