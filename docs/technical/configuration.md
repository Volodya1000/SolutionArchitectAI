# Конфигурация и секреты

[Навигация](README.md) · [Развёртывание](deployment.md)

## Модель настроек

Рекомендуется Pydantic Settings с тремя логическими разделами, загружаемыми в composition root один раз при старте.
Use cases получают только нужные типизированные параметры, а domain не читает файлы, окружение или глобальный Settings.

| Раздел | Примеры | Источник |
| --- | --- | --- |
| EnvironmentSettings | Режим запуска, bind host/port, URL LLM endpoint, пути данных, CORS origins | Процесс, локальные dotenv; значения зависят от окружения |
| SecretsSettings | API-ключи, пароли, токены, закрытый ключ сертификата | Production secret files или локальный dotenv/окружение |
| AppSettings | Alias/идентификаторы моделей по ролям, temperature, token budget, deadline, число попыток и лимиты агентов | Версионируемый `config/app.yaml`, разрешённые env overrides |

URL/порт сами по себе обычно не секреты; URL с credentials/query token считается чувствительным и не выводится в лог.
Приватный hostname может быть внутренней информацией без права публикации, хотя он не является паролем.
Alias модели не раскрывает API-ключ: секрет разрешается отдельно в инфраструктурном адаптере.
YAML приложения не является архитектурным манифестом A-06 и не смешивается с данными проектируемых систем.

## Файлы и Git

| Файл | Назначение | Git |
| --- | --- | --- |
| `.env.example` | Все обязательные env-поля с безопасными примерами и пояснением чувствительности | Хранится; без действующих ключей |
| `.env` | Локальная базовая конфигурация backend, при необходимости локальные секреты | Игнорируется даже если сейчас содержит только URL |
| `.env.local` | Личные переопределения поверх `.env` | Игнорируется |
| `.env.local.example` | Только при наличии отдельного полезного набора личных настроек | Не обязателен; иначе дублирует `.env.example` |
| `config/app.yaml` | Общие несекретные параметры приложения | Хранится и проходит ревью |
| `config/app.production.yaml` | Необязательный несекретный overlay, если production действительно отличается | Может храниться; не создаётся ради имени окружения |

В будущем `.gitignore` явно исключает `.env`, `.env.local`, `.env.*.local`, каталоги secret files, рабочие проекты и traces; шаблоны `.example` остаются разрешёнными.
Одного ignore недостаточно: секреты не добавляются в fixtures, Docker context, диагностический dump Settings или историю проектов.
Сейчас реальные env/YAML/ignore-изменения не создаются; таблица задаёт правила будущего PR.

## Приоритет загрузки

Это явная политика проекта, а не предположение о стандартном порядке Pydantic Settings.
Источники настраиваются через [settings_customise_sources](https://docs.pydantic.dev/latest/concepts/pydantic_settings/#customise-settings-sources); ранее указанный source имеет больший приоритет.
Префикс backend — `SAA_`, вложенные поля отделяются `__`; имена чувствительных и обычных полей не пересекаются.

| Раздел | Порядок от высшего к низшему |
| --- | --- |
| EnvironmentSettings | Явные init overrides только тестового bootstrap → окружение процесса → `.env.local` → `.env` → безопасные defaults |
| SecretsSettings, development | Init overrides тестов → окружение → `.env.local` → `.env`; реальных default-ключей нет |
| SecretsSettings, production | Secret files → разрешённое окружение; dotenv и тестовые init overrides выключены |
| AppSettings | Init overrides тестов → разрешённые `SAA_APP__…` окружения → local dotenv overrides в development → явный YAML overlay → `config/app.yaml` → defaults |

Production режим и пути конфигурации выбираются bootstrap из аргумента запуска/окружения до загрузки файлов, а не из YAML, способного изменить режим собственной проверки.
Наличие значения одновременно в secret file и env в production считается ошибкой неоднозначной настройки: указанное преимущество файла не скрывает забытый старый ключ.
В production общие dotenv не читаются даже при случайном наличии в рабочем каталоге; необязательные локальные файлы в development могут отсутствовать.
Указанный явно YAML-файл/secret file при отсутствии или ошибке чтения останавливает запуск; обязательный ключ выбранного провайдера не заменяется заглушкой.
`.env.example` никогда не загружается как источник. Пути определяются от явного config root, а не поиском `.env` по родительским каталогам.

Для AppSettings подходит [YamlConfigSettingsSource](https://docs.pydantic.dev/latest/concepts/pydantic_settings/#other-settings-source).
Рекомендуем обёртку source с безопасным YAML-парсером, отклонением дубликатов и проверкой допустимых ключей до Pydantic, чтобы опечатка не исчезла при merge.
Документация Settings сама по себе не гарантирует строгий контроль дубликатов YAML; используем политику парсера из [backend.md](backend.md#предметная-модель-ввод-и-артефакты).
Overlay сливается по именам вложенных полей, список заменяется целиком; не полагаемся на неявную семантику deep/shallow merge версии библиотеки.
Сначала проверяется каждый слой, затем результирующий объект. Неизвестные ключи YAML и неизвестные prefixed `SAA_` переменные отклоняются отдельной проверкой bootstrap; произвольные системные env игнорируются.
Разделы Settings получают только свои namespaces: общий dotenv фильтруется по ним, чтобы поля соседнего раздела не давали ложный `extra` error.
Выбор источников и приоритеты покрываются integration-тестом: это существенный контракт конфигурации, а не возможность для ручного толкования.

## Содержимое YAML и проверки запуска

YAML задаёт role → model alias, provider model ID, параметры генерации, context budget, concurrency, deadline и общий лимит попыток.
URL endpoint/ключ не дублируются в YAML; конфигурация роли ссылается на профиль подключения из EnvironmentSettings/SecretsSettings.
Обычные параметры доступны и локальному провайдеру; API-ключ обязателен только для подключения, которое действительно требует его.

1. Прочитать и проверить схемы всех источников, отвергнуть дубликаты и неизвестные поля.
2. Проверить положительные лимиты, допустимые пути/URL, отсутствие credentials в публичных URL и согласованность времени ожидания.
3. Проверить роли, существование alias и разрешённые параметры выбранной пары provider/model; temperature и другие неподдерживаемые параметры не задаются автоматически всем моделям.
4. Проверить суммарный context/output budget и общую политику retry: никакого произведения независимых SDK-повторов.
5. Проверить доступность локального каталога, Git/рендерера и права записи; внешняя LLM не вызывается платно для каждого health check.
6. Зафиксировать безопасное резюме эффективной конфигурации и её версию/хеш без секретных значений; при ошибке не обслуживать API как ready.

Границы token budget оцениваются с запасом и уточняются адаптером: общий токенизатор не гарантирует точного счёта для каждого провайдера.
Изменение настроек применяется рестартом, без hot reload посреди операции; уже запущенный run сохраняет эффективные параметры.
Ключи не входят в fingerprint и Git-снимки; версия инструкций и несекретные параметры важны для воспроизведения по [agents.md](agents.md).
SecretStr маскирует стандартное представление, но не шифрует файл и не защищает произвольный вывод; redaction проверяется отдельно.

## Production и frontend

Production-секреты рекомендуется получать от механизма секретов платформы в файлах с минимальными правами, доступных только backend.
В Compose это `/run/secrets/…`; локальный Compose предоставляет file mounts, а не полноценный зашифрованный vault.
Файлы на хосте защищаются отдельно; ротация — замена секрета и контролируемый рестарт. Build args, Dockerfile и образы секретов не содержат.
Передача через env допустима как ограниченная альтернатива для выбранного окружения с учётом доступности env процессам и средствам диагностики.
Конкретный production secret manager выбирается вместе с платформой, не является новой зависимостью локального MVP.

Frontend имеет отдельный `frontend/.env.example` только для публичных параметров; по умолчанию достаточно относительного `/api`.
Backend dotenv не передаётся сборщику frontend и не копируется в static image.
[Vite встраивает `VITE_*` при сборке](https://vite.dev/guide/env-and-mode); туда нельзя помещать ключи LLM или закрытые URL с токенами.
Изменение env контейнера после сборки не меняет эти константы; для текущего same-origin подхода runtime-конфигурация браузера не нужна.
Различие между dotenv приложения, интерполяцией Compose и env процесса контейнера описано в [deployment.md](deployment.md).
