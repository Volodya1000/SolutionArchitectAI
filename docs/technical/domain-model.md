# Предметная модель и представления

[Навигация](README.md) · [Backend](backend.md)


Один репозиторий на корпоративное пространство: каталоги систем, компонентов, данных, интерфейсов, отношений, интеграций, решений и оснований. Проекты/задачи выбирают ID общего каталога. Повторное использование не создаёт копию; одноимённые объекты не объединяются автоматически без проверки идентичности человеком.

`View` имеет устойчивый ID, folder_id, viewpoint/profile и ссылки на общие объекты/отношения. `ViewNode` имеет свой ID и object_id; `ViewEdge` — relationship_id и ссылки на визуальные узлы. Позиции, scale, группировки, label override и style принадлежат виду. Отношение имеет собственные концы и свойства; визуальная линия не меняет его семантику. Изменение общего имени обновляет все виды, кроме явно заданной локальной подписи; UI показывает наличие override. Поиск «где используется» вычисляется по ссылкам.

При удалении общего объекта сначала показывается влияние на отношения и виды; висячие ссылки запрещены. Удаление из одного вида сохраняет каталог. После изменения общего объекта пересоздаются зависимые проекции, сбрасывается актуальность проверок; layout других видов сохраняется. Графовые проверки выполняются на заявленном срезе, не требуют соединить весь корпоративный каталог.

Хранение — **JSON**. Рекомендуемая раскладка: `model.json` со schema_version и ID пространства, `objects/<id>.json`, `relationships/<id>.json`, `views/<id>.json`, `view-tree.json`, `decisions/<id>.json`, `sources/<id>.json`, `checks/`. Несколько файлов уменьшают конфликтность diff. UUID назначает приложение; имена и aliases можно менять без смены ID. Schema version имеет явные миграции; неизвестная версия отклоняется, исходный снимок сохраняется.

UTF-8, фиксированные отступы и newline, сортировка ключей; множества сортируются по ID, последовательности (порядок узлов дерева/точек линии) сохраняют смысловой порядок. В модель не добавляются плавающие timestamps ради сериализации. Одинаковые входы и версия сериализатора дают одинаковый JSON. Duplicate JSON keys отклоняются стандартным decoder hook, не скрываются последним значением. JSON Schema проверяет форму; независимые domain-валидаторы — ссылки, типы концов, ограничения и правила. UI и LLM-кандидаты проходят те же валидаторы. Обычный пользователь не редактирует JSON вручную.

Таблицы A-01–A-07, .puml и SVG — проекции одной редакции, не независимые модели. Рендерер получает проверенный срез и профиль; исходный LLM-текст не исполняется как PlantUML. Без LLM повторный рендер сохраняет смысл и ID. Ошибка рендера оставляет предыдущий экспорт с явной старой редакцией. Направление данных, инициатор вызова, ответ и Access read/write хранятся отдельно. Exchange XML рассматривается отдельно после решения по экспорту в Archi.

Markdown/текст — первый документный вход с оригиналом, SHA-256 и локаторами фрагментов. PDF/DOCX/Docling оцениваются на цитируемость при расширении набора. Формализация правил — подтверждаемая человеком привязка версионируемого источника к виду чистого валидатора и типизированным параметрам, области и исключениям. ИИ не исполняет текст правила как Python/eval/DSL. Неизвестная обязательная проверка остаётся «не проверено», а не «пройдено».

## Авторитетная модель и цикл изменения

**Источник предметной логики — независимая модель системы, представленная Python-доменными классами с валидаторами.** Во время выполнения она определяет архитектурные сущности, допустимые операции и инварианты. Git хранит авторитетную зафиксированную редакцию данных; JSON — формат её сериализации, сохранения и восстановления. JSON Schema определяет форму сохранённого представления, а не бизнес-логику архитектуры.

1. Создать Python-доменные объекты или восстановить их из сохранённой редакции.
2. Выполнить разрешённые предметные операции над кандидатом.
3. Проверить доменные инварианты.
4. Синхронно проверить ссылочную целостность, обязательные атрибуты, уникальность ID и синтаксическую корректность; при ошибке сохранить черновик без коммита.
5. После решения человека сериализовать структурно корректную модель в детерминированный JSON и сохранить коммит в рабочей ветке по протоколу [публикации](persistence.md).
6. Асинхронно проверить топологию и архитектурные правила; результаты записать в A-07. Открытые нарушения препятствуют итоговому согласованию и merge, но не промежуточным коммитам.

При чтении допустимы предварительные проверки синтаксиса/структуры JSON, включая duplicate keys и версию формата. Затем обязательны восстановление Domain и его валидация. Корректный JSON не доказывает корректности архитектуры. Основные бизнес-правила не переносятся в JSON Schema; классы Domain не генерируются из `model.schema.json` документарного примера.

Сериализация/восстановление — отдельные механизмы в адаптере сохранения, с явным mapping и версионируемыми миграциями. Domain не импортирует JSON, ORM, HTTP или LLM SDK; Application вызывает предметные операции через Python-объекты, а не через файловые DTO. Текущий пример проверяет только документарный эталон. Проектирование классов, операций, round-trip и инвариантов относится к последующим PR разработки.

Происхождение, статус контроля качества и решение человека — три независимые характеристики. Контроль имеет четыре значения: «Подтверждено», «Требует проверки», «Нарушение», «Недостаточно данных». Приоритет: доказанное нарушение → недостаток обязательных данных → требует проверки → подтверждено при выполнении всех условий. Подтверждение проверками не является approval. Результат конкретного check и его пояснение не подменяют итоговый статус; статус привязан к актуальным входам/области. Изменение затронутых зависимостей снимает его актуальность, обязательная непроверенность блокирует согласование. Статусы проверки покрытия неформализованного требования «Не проверено (требует ручной верификации)» и «Подтверждено человеком» существуют отдельно от четырёх статусов контроля объектов и связей.
