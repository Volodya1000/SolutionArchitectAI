# PR 3: проверка уточнений и обсуждений

## Приёмочные входы

- [Полный BRD](../examples/pr3/reporting-system-complete.md).
- [Неполный BRD](../examples/pr3/reporting-system-incomplete.md).

Оба файла содержат предметные части I и II исходного примера. Единственное
различие — в неполном файле отсутствует последнее предложение R-04 о реакции
на дату вне окна. R-03, окно 30 дней, пустая сводка и корпоративные правила
сохранены. Проверка этого контракта: `backend/tests/unit/test_pr3_inputs.py`.

## Воспроизведение

Из корня репозитория:

```powershell
uv run --locked --project backend python -m tools.quality setup
uv run --locked --project backend python -m tools.quality full
```

`full` создаёт отдельный Compose-проект с fake LLM, PostgreSQL, временными
томами и случайными портами. Он проверяет миграции на новой базе, интеграционные
тесты, Playwright и восстановление после сбоев. Рабочий проект разработчика и
его локальная модель не используются.

Для ручной проверки запустите приложение по [инструкции развёртывания](deployment.md).
На каждом независимом прогоне выбирайте одну версию документа и
«Начать с новой историей уточнений».

## Браузерные шаги А–Г

1. **А. Обсуждение пробела.** Загрузить неполный файл, запустить извлечение.
   Ожидается блокирующий вопрос о реакции на дату вне окна. Открыть «Обсудить»
   у R-04 и отправить «Срок хранения уже указан. Что именно нужно уточнить?».
   Ответ должен различать известный срок из R-03 и отсутствующую реакцию R-04,
   содержать ссылки на источники. Свободный разговор оставляет вопрос открытым.
2. **Б. Сохранение и продолжение.** Закрыть вкладку, перезапустить backend и
   PostgreSQL с сохранением томов. Открыть чат из списка: видны прежние сообщения,
   вопрос и исходный фрагмент. Явно сохранить ответ «Отклонять запрос и показывать
   допустимый диапазон дат». Анализ завершается; требование содержит добавление
   архитектора, автора, время и основание. Исходная цитата не изменяется.
   История содержит один вопрос и одно решение.
3. **В. Допущение.** В новом прогоне принять допущение, указав основание,
   ответственного, условие проверки, последствия и снижение риска. Анализ
   продолжается, A-01 показывает «Подлежит верификации», ссылка открывает A-07.
   Подтверждение закрывает риск. Отклонение с причиной сохраняет прежний
   завершённый результат и решение, открывает ревизию вопроса 2 и цикл 1 на том
   же `thread_id`. Новый ответ завершает цикл 1 без повторного извлечения.
4. **Г. Полный источник и редакции.** Загрузить полный файл с новой историей.
   Реакция уже указана: необоснованная блокировка не ожидается. Обсуждение
   доступно и у полного требования. Открыть отдельное обсуждение фрагмента
   прямо из «Документов», загрузить v2 этого документа, затем по обратной ссылке
   старого чата открыть исходную v1 с прежним выделением.

Автоматизация этих действий находится в `frontend/e2e/clarifications.spec.ts`.
Fake LLM проверяет поведение приложения; семантическая точность реальной модели
оценивается отдельно.

## Четыре дополнительные проверки

| Условие | Проверяемый результат |
| --- | --- |
| Ответ против допущения | Две PostgreSQL-транзакции и два разных `operation_id`: одно решение, второй HTTP 409; нет побочных записей проигравшей команды; повтор победившей возвращает сохранённый результат |
| Два независимых блокера | После первого ответа обновлённое требование уже доступно; второй вопрос открыт и общий анализ ждёт; завершение после второго ответа |
| Один фрагмент, две истории | Чат с явным анализом получает только его историю; чат без анализа получает источник без ответов обеих историй |
| Отклонение после завершения | Предыдущий завершённый цикл сохранён; новая ревизия и причина видны; тот же поток, без повторного извлечения, включая потерянный checkpoint завершения |

Тесты команд и HTTP проверяют потерю ответа после commit, повтор с изменённым
payload, устаревшую ревизию, чужую задачу, отсутствие прав и неизменность
сохранённого результата при недоступности файла после успешной команды.
Тесты графа проверяют освобождение слота/контекста/SQL, ожидание на следующий
день без расходования активного бюджета, отмену и ошибку после возобновления.

## Результаты проверок

27.11.2026 команда `uv run --locked --project backend python -m tools.quality full`
завершилась с кодом 0. Зафиксированы:

- 86 frontend-тестов, lint/format/typecheck, сборка и архитектурные проверки;
- 254 быстрых Python-проверки и 16 проверок самих quality gates;
- 161 интеграционный тест на новой PostgreSQL после миграций 0001–0007;
- покрытие backend 92,66% при обязательном пороге 90%;
- 23 Playwright-сценария, включая все 9 сценариев PR 3;
- runtime smoke: обрыв SSE, отмена, graceful shutdown, аварийный перезапуск,
  перезапуск/недоступность PostgreSQL и независимость историй;
- аудиты обоих наборов зависимостей без известных уязвимостей.

После заключительного уточнения отпечатков отдельно прошли ещё 31 проверка:
5 проверок независимости отпечатка от разбиения фрагмента, 3 проверки агента,
10 сценариев истории и 13 PostgreSQL/API-сценариев `ResumeRun`. Все они включены
в обычный набор CI и обязательные хуки. Отпечаток учитывает полное содержимое
и область документа; изменение размера модельного контекста не считается
изменением источника. Неполное покрытие не совпадает с полным фрагментом.

Два независимых ревью в отдельных worktree проверили SQL, граф, историю,
обсуждения и frontend. Исправлены найденные проблемы привязки редакций,
переноса ответов, изоляции ревизий, восстановления завершённого checkpoint,
пересмотра общего допущения и сохранности нового черновика. Заключительное
ревью не оставило важных или критических замечаний. Отдельный тест SQL-блокировок
проверяет отсутствие удержания вопроса при ожидании другого анализа.
Новые решения не возобновляют отменённый или завершившийся ошибкой анализ;
повтор ранее успешной команды возвращает сохранённый результат.

## Реальная локальная модель

Проверен локальный LM Studio **0.4.13+1** (ProductVersion 0.4.13.0), endpoint
`http://127.0.0.1:1234/v1`; backend использует `host.docker.internal:1234/v1`.
Загружена `qwen2.5-coder-14b-instruct` от lmstudio-community, GGUF **Q4_K_M**,
контекст **12288**, одна параллельная генерация. Профиль приложения:
`native_json_schema`, output limit 6912, temperature 0.2, служебный резерв 256,
2 символа/токен, timeout запроса 600 с, активный deadline 1800 с, максимум
128 запросов, 1 сетевой повтор и 2 валидационные коррекции. Контракт извлечения
`requirements-1`, промпт `extract-2`. Использовался отдельный Compose-проект
`saa-quality-pr3-model` с собственными PostgreSQL и томами.

Команды воспроизведения против запущенного локального приложения:

```powershell
uv run --locked --project backend python -m tools.clarification_smoke --base-url http://127.0.0.1:8080 --source docs/examples/pr3/reporting-system-complete.md --output .build/pr3-complete.json --timeout 1800
uv run --locked --project backend python -m tools.clarification_smoke --base-url http://127.0.0.1:8080 --source docs/examples/pr3/reporting-system-incomplete.md --output .build/pr3-incomplete.json --timeout 1800
```

Каждый вызов загружает одну неизменяемую версию и запрашивает новую историю.
Адрес приложения нужно заменить своим опубликованным локальным портом;
это адрес приложения, а не LLM endpoint. Веса и настройки LM Studio не менялись.

`requirements[n].normalized_text`: в неполном прогоне 10 полей на первой
попытке и по 11 на следующих. Цитаты содержали 87–395 кириллических букв,
результаты — 0 кириллических, 88–404 латинских букв, 17–81 слово. Это
существенная смена языка, а не короткое техническое имя. Проверка правильно

**Семантическое качество уточнений на этой модели не оценено**: нет фактических
вопросов и ссылок для сравнения, нельзя оценить пропущенные условия, ложные
блокировки, распознавание единственного различия или ответы чата. Успех fake
сценариев не подтверждает эти свойства реальной модели.

оценивается по отдельным фактическим результатам, а не по fake.

предложения с diff или графический редактор последующих этапов.
