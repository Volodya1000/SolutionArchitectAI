# Frontend и пользовательский интерфейс

[Навигация](README.md) · [Агенты](agents.md) · [Проверки](quality-and-testing.md#frontend)

## Стек и центр интерфейса

Отдельное React + TypeScript strict + Vite SPA, React Router для адресуемых пространства/задачи/вида/редакции, TanStack Query для серверного состояния. SSR не требуется; FastAPI владеет правилами, LLM и хранилищами. Stream Chat с обязательным hosted backend не подходит.

Центральный объект — общая архитектурная модель и дерево представлений. Рядом доступен чат, основной способ общения с ИИ. Пользовательский интерфейс позволяет найти компонент, открыть свойства/отношения, список использующих его видов, связанные требования/решения, историю и diff. Задача выбирает ветку, но не создаёт отдельную архитектуру. Представления — ссылки на общие ID, не набор независимых SVG. Полный drag-and-drop редактор уровня Archi вне первого MVP.

## Выбранные библиотеки

Планируется использовать **shadcn/ui + Tailwind CSS** для общих компонентов и тем, **assistant-ui** для чата, **React Flow (`@xyflow/react`)** для интерактивных диаграмм. React Router работает в Declarative mode; TanStack Query отвечает за серверные данные без дублирования кеша в Router. Vite обеспечивает dev server и сборку SPA. Основания, альтернативы, лицензии, peer ranges и ограничения зафиксированы в [анализе библиотек](frontend-library-evaluation.md), проверенном 12 ноября 2026 года. Выбор сделан; интеграционный smoke и lock-файл ещё предстоят.

**Material Design не является отдельной design system проекта.** Отдельные общие UX-принципы Material Design могут использоваться как reference, но компоненты, design tokens и визуальный язык определяются shadcn/ui + Tailwind CSS.

assistant-ui использует ExternalStoreRuntime и собственный адаптер FastAPI: серверная история, stream, список чатов, вложения, восстановление и отмена run. Облачные chat services не нужны. Карточки уточнений/предложений и их команды реализует приложение. shadcn-компоненты копируются в проект: команда отвечает за их обновления и доступность. Redux не требуется: Query хранит серверное состояние, React — локальные правки.

## Чат и команды

Несколько чатов привязываются к задаче либо пространству. Сообщения имеют устойчивые IDs и typed parts: text, file reference, clarification, proposal, review, run status/error. PostgreSQL — авторитет истории. Streaming текст не превращается в подтверждённую архитектуру. UI показывает queued/running/waiting_input/cancelling/cancelled/failed/completed и incomplete output; сервер подтверждает окончательную отмену.

SSE/fetch-stream использует run_id и event sequence, reconnect загружает сохранённый статус/сообщение без второй генерации. Остановка чтения потока и отмена server run — разные действия. Переключение чата не перемешивает потоки. Вложения идут через file API, с типом, размером, доступом и immutable version; ошибки upload не маскируются успешным сообщением.

Карточка вопроса показывает blocking и основание; ответ отправляет AnswerClarification. Карточка proposal показывает diff, источники, затронутые общие объекты/виды, формальные нарушения и замечания judge; принять/отклонить — application-команды. Свободное «согласен» не скрытый approval. Для подтверждения пользователь видит точную ревизию/область. Несохранённый ввод сохраняется при обновлении server state.

Mutation применения передаёт expected_commit/operation_id. Запись не обновляется оптимистически; при потере ответа запрашивается статус операции. Query retry для mutating commands выключен; повтор той же команды идемпотентен на сервере. Cache keys включают workspace/task/revision/run; late response другого чата не заменяет текущий. Raw HTML из Markdown и активный SVG не исполняются.

## Светлая и тёмная темы — MVP

Обязательны **Light / Dark / System**, ручное переключение и восстановление выбора. System реагирует на prefers-color-scheme; явный Light/Dark имеет приоритет. Предпочтение сохраняется локально и в пользовательских настройках PostgreSQL; при старте локальный выбор применяется до загрузки профиля, затем действует сохранённый выбор пользователя с явной политикой синхронизации.

[ThemeProvider shadcn/ui для Vite](https://ui.shadcn.com/docs/dark-mode/vite), localStorage и CSS variables образуют общую тему. Не добавляем next-themes из Next.js примеров; assistant-ui и React Flow используют те же tokens и согласованные палитры.

Общие tokens применяются к чату, таблицам, дереву, диалогам, карточкам, diff, Markdown/code blocks и замечаниям. Диаграммы получают собственные проверенные палитры background/text/line/fill в обеих темах; если SVG экспортируется только для светлого режима, показывается на явно светлой canvas с читаемой рамкой, а не на прозрачном чёрном фоне. Не используем CSS invert: он меняет смысл цветов. Смена темы не меняет предметную модель/layout; theme-specific SVG остаётся производным экспортом той же ревизии.

## Читаемость и структура

Архитектор работает часами: приоритет читаемым шрифтам, умеренной плотности, контрасту и отсутствию визуального шума. Длинные таблицы имеют закреплённую шапку/локальный scroll, дерево — поиск и клавиатуру, диаграмма — zoom/pan и доступную табличную альтернативу. Статусы различаются текстом, не одним цветом. Подробные объяснения/источники раскрываются по запросу; основной экран выделяет сомнительные предложения ИИ, особенно конфликтующие с решениями человека, без баллов на каждом элементе.

Рекомендуем WCAG 2.2 AA как цель проверки доступности, не уже полученную сертификацию. Focus, labels, контраст, 200% zoom, screen reader и длинные русские тексты проверяются в обеих темах; live announcements streaming дозированы. Узкий экран использует вкладки с сохранением ввода. Git diff показывает JSON/.puml с понятными названиями объектов; JSON не обычный редактор архитектуры.

Предлагаемая структура: `app/` (router/providers/theme), `pages/` (композиция), `features/` (workspace-tree, object-details, tasks, chat, proposals, verification, artifacts, history), `shared/api` и `shared/ui`. Shared не импортирует features/pages; нет циклических barrel exports. Направления импортов `app → pages → features → shared` и отсутствие циклов контролируются `eslint-plugin-boundaries` и `eslint-plugin-import-x`; для взаимодействия features выбираются публичные контракты, а не внутренние пути. Правила сложности и вложенности обработчиков/хуков, React Refresh и усиленный TypeScript перечислены в [плане проверок](quality-and-testing.md#frontend). OpenAPI-типы можно генерировать, но они не заменяют runtime server validation.

## Графическое редактирование и review MVP

Основной рабочий инструмент архитектора — интерактивное графическое представление общей модели. MVP поддерживает выбор узла/отношения, изменение свойств общего объекта, добавление/изменение разрешённого отношения, переход к связанному виду и поиск всех представлений объекта. Изменение layout локально виду. Изменение семантики идёт через предметную команду, проверки и решение человека, с анализом влияния на другие виды.

Предложение ИИ показывается в контексте затронутых объектов и diff; доступны применить/отклонить/вернуть на уточнение. Сравнение показывает добавление, изменение и удаление объектов/связей с основаниями, а не только текст сериализации. Интерфейс выделяет доказанное нарушение, конфликт с решением человека, недостающие обязательные данные и сомнительное предложение; подробности раскрываются. Контроль качества, происхождение и human approval независимы.

**React Flow выбран** для controlled nodes/edges, selection, drag, handles/reconnect, custom nodes/edges и zoom/pan. Приложение сохраняет по view ID отдельные позиции, подписи и viewport, отображает свойства и where-used, проверяет разрешённые отношения на backend и строит semantic diff с принятием/отклонением. ID графического экземпляра и ID общего предметного объекта различаются. React Flow не становится источником предметной модели или Git-форматом.

PlantUML получает проверенную проекцию той же предметной редакции и генерирует экспортируемые схемы; SVG не заменяет интерактивный редактор. Будущий ArchiMate Model Exchange XML строится отдельным адаптером предметной модели, не сериализатором React Flow. Это не замена ArchiMate на UML. MVP ограничен согласованным профилем нотации; полный редактор Archi не обещается. Интеграционные проверки охватывают select/edit edge, where-used, два независимых layout, русские подписи, темы, клавиатуру и diff.

## Минимальный контракт Run и streaming

Первый чат поддерживает queued → running → completed/failed либо queued/running → cancelling → cancelled. waiting_input добавляется с агентным HITL. Терминальные состояния неизменяемы; гонка завершения и отмены разрешается атомарным переходом на сервере. incomplete — признак незавершённого вывода, а не успешное завершение; частичный текст сохраняется при ошибке, отмене или прерывании процесса.

### Согласование и восстановление в PR 2

HTTP и SSE обновляют единый Query-кеш с одним правилом: для каждого run сохраняется
снимок с максимальным sequence. Согласование выполняется при записи в кеш, поэтому
задержавшийся HTTP-ответ не откатывает текст, статус или уже добавленные сообщения.
Ошибка фонового обновления показывает предупреждение поверх доступной переписки;
экран первоначальной ошибки используется только при отсутствии данных.

Защищённый адаптер sessionStorage хранит черновики и описания команд с резервом
в памяти при исключениях чтения, записи или удаления. Черновик анализа включает
точные version IDs и уточнение, а ключ содержит область workspace/task. Неопределённая
загрузка хранит operation ID, целевой документ, имя, размер и SHA-256; объект File
не сериализуется. После повторного открытия проверяется результат операции. Если
нужен повтор, пользователь выбирает тот же файл, который сверяется до отправки.
Запуск анализа восстанавливается по operation ID независимо от истории и сохраняет
исходную команду до выяснения результата. Резерв в памяти переживает навигацию;
перезагрузка браузера требует доступного sessionStorage.
Повтор сохранённой команды не зависит от текущего выбора версий или загрузки
истории: его доступность определяется проверкой конкретной операции.

Список документов содержит latest_version, а полный список редакций читается
только при раскрытии карточки. История анализов использует страницы по 50 кратких
записей; выбранный активный запуск опрашивается отдельным status-запросом. Полные
кандидаты и источники загружаются для завершённого запуска. Отдельный matching-запрос
находит активный или завершённый анализ точного набора версий и уточнения независимо
от страницы истории. Контракты перечислены в [описании backend](backend.md#компактные-запросы-для-интерфейса).

PUT настроек темы сериализован общей очередью мутаций: следующий выбор отправляется
после завершения предыдущего запроса, включая его ошибку. Локальный выбор применяется
сразу. Стили подключаются из одного входного файла; tokens, база, общие UI-элементы,
оболочка и features хранятся отдельно. Общий surface-card задаёт оформление карточки,
а feature-классы отвечают за её содержимое. Цвета ошибок подключаются после
feature-стилей, чтобы статусы сохраняли семантический цвет.

Команда запуска возвращает run_id; повтор с тем же идентификатором команды не создаёт второй run. SSE-события содержат run_id, монотонный sequence, тип и payload (дельта текста, изменение статуса, ошибка). История и статус читаются отдельным запросом из PostgreSQL. При reconnect клиент получает сохранённый снимок с последним sequence и продолжает получать новые события без повторной генерации; пропущенные дельты восстанавливаются снимком, дубликаты игнорируются. Закрытие соединения не отменяет run. Отдельная идемпотентная команда отмены запрашивает остановку; cancelled фиксируется после прекращения локальной обработки и освобождения ресурсов, без обещания остановки вычислений удалённого сервера. После restart незавершённый чат не объявляется completed и не перезапускается автоматически.
