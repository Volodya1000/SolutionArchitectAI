## Рекомендуемый стек

Отдельное приложение React + TypeScript в strict-режиме, собираемое Vite в статическую SPA.
Backend остаётся единственным владельцем предметных правил, Git, LLM-ключей и окончательного решения о допустимости команды.
TypeScript помогает согласовать интерфейсы, но не проверяет произвольный HTTP-ответ во время выполнения и не заменяет серверную валидацию.

| Выбор | Почему подходит проекту | Альтернатива и условие пересмотра |
| --- | --- | --- |
| React + TypeScript | Большой выбор компонентов для чата, форм, таблиц и работы с async; типы уменьшают ошибки связей API | Vue/Svelte также пригодны, но не дают здесь преимущества, оправдывающего смену основного кандидата |
| Vite SPA | Быстрый локальный цикл, статическая поставка, отдельный Python API; SEO/SSR не требуются рабочему месту архитектора | Next.js/React Router framework mode — при потребности SSR/RSC; Parcel/Rsbuild — другие сборщики без явной пользы для текущего объёма |
| React Router, declarative mode | Адресуемые проект, артефакт и история, вложенные страницы без второго механизма загрузки данных | TanStack Router — более строгая типизация маршрутов ценой нового API; data/framework mode — при потребности loaders/SSR |
| TanStack Query | Серверные проекты, снимки, proposals, отчёты и runs: кеш, loading/error, обновление после mutation | SWR удобен для чтения; fetch/useEffect потребует самостоятельно поддерживать кеш и гонки; RTK Query полезнее при уже выбранном Redux |
| Material UI, бесплатный core | Готовые формы, панели, диалоги, таблицы и обратная связь; меньше самостоятельной работы для команды без frontend-опыта | Radix/shadcn + Tailwind дают больше контроля, но требуют самостоятельно собирать дизайн-систему; Ant Design — разумный вариант для преимущественно табличного UI |

React в [официальном руководстве](https://react.dev/learn/build-a-react-app-from-scratch) рекомендует оценить framework: SPA означает собственный выбор routing и data fetching.
Здесь эти две обязанности явно закрыты React Router и TanStack Query, а серверные функции уже принадлежат FastAPI.
Режимы маршрутизатора отличаются по возможностям, см. [React Router](https://reactrouter.com/start/modes); его loaders не дублируют Query-кеш.
Возможности TanStack Query относятся к [серверному состоянию](https://tanstack.com/query/latest/docs/framework/react/overview), а не к авторитетной модели в браузере.

## Состояние и команды

| Вид данных | Где живёт |
| --- | --- |
| Выбранный проект, артефакт, редакция, вкладка | URL/search params, чтобы сохранить ссылку и работу Back/Forward |
| Снимки модели, история, run status и отчёты API | TanStack Query; ключи включают project_id и revision/run_id |
| Несохранённый ввод чата, формы/YAML, раскрытые панели | useState/useReducer в соответствующей фиче |
| Тема и немного общих UI-настроек | React Context; не копия предметной модели |

Redux не требуется: серверное состояние уже обрабатывает Query, локальное — React.
Zustand рассматривается при появлении сложного общего клиентского состояния; он также не добавляется заранее.
Состояние «ввод отредактирован» отделено от «применено», «сохранено Git» и «согласовано».
Автоматическое обновление Query не затирает dirty-редактор: показывается новая серверная редакция и необходимость сравнения.
Кандидат и подтверждённая версия показываются раздельно; ошибочный ввод остаётся видимым с диагностикой и прежней корректной моделью.

Mutation применения отправляет expected_commit и idempotency key, блокирует повтор кнопки до ответа и не меняет канонический кеш оптимистически.
При потере ответа UI запрашивает статус операции/повторяет ту же команду с тем же ключом; HTTP 409 предлагает сравнить и пересоздать предложение.
После успеха инвалидируются текущий снимок, история и зависимые артефакты; immutable cache старых редакций сохраняется.
Query retry для команд записи выключен; чтения имеют ограниченный retry, run polling прекращается на terminal status.
Поздний ответ другого проекта/редакции не заменяет текущий экран; используются отдельные query keys и отмена запросов.

## Интерфейс по сценариям SolutionArchitectAI

Чат — основной способ объяснить намерение, задать вопрос, ответить на уточнение и получить предложение с основанием.
Подтверждение предметного изменения и согласование этапа имеют отдельные понятные действия; сообщение «согласен» обрабатывается use case с явным указанием области/редакции, а не скрытым изменением UI-флага.
Рабочая область проекта соединяет чат с A-01–A-07: таблицы/формы, YAML, диаграммы, замечания и историю.
Панель предложения показывает diff, происхождение, затронутые решения, формальные ошибки и отдельные замечания judge; кнопка утверждения зависит от серверного результата проверок.
Ошибки YAML показывают путь/строку и причину, предметные — объект и правило; неблокирующие вопросы остаются доступны.
Пользовательские названия русские и понятные; служебные ID не требуется вводить вручную.

Для MVP достаточно MUI Table и обычных форм; платные DataGrid-возможности не предполагаются.
Короткие формы используют контролируемые поля; React Hook Form можно добавить при появлении сложных связанных форм, не как обязательный слой для каждого поля.
YAML сначала редактируется доступным текстовым полем; CodeMirror — вариант следующего улучшения при необходимости подсветки/навигации по диагностике.
Диаграммы — backend SVG плюс скачивание .puml и YAML; Mermaid/React Flow не заменяют требуемую нотацию ArchiMate и не вводят графический редактор в MVP.
Для SVG рекомендуем показ как изображения, без вставки непроверенного XML в DOM; масштабирование и скачивание достаточны на первом этапе.
Ответы чата — текст/безопасно отрисованный Markdown без raw HTML; произвольные ссылки и HTML из LLM не исполняются.
Текстовый diff YAML/.puml достаточен по FR-11; библиотека diff выбирается в PR истории после проверки русских текстов и лицензии.

## Material Design, адаптивность и доступность

[Material UI](https://mui.com/material-ui/getting-started/) реализует Material Design 2; её использование само по себе не означает полного соответствия Material 3.
Рекомендация — согласованная тема MUI, ограниченный набор компонентов и принципы актуального [Material Design](https://m3.material.io/foundations/): иерархия, ясные действия, feedback, адаптивность и доступность.
Не требуется копировать анимации/оформление Google или самостоятельно реализовывать все компоненты M3.
Финальное расположение чата и результатов согласуется на отдельном статическом прототипе; этот документ не утверждает макет.

На широком экране допустимы соседние области чата и результата; при нехватке ширины — последовательные вкладки/панели с сохранением ввода.
Таблица может прокручиваться внутри области, но действия и ошибки остаются доступны; размер диаграммы не должен растягивать всю страницу.
Предлагаемая цель — [WCAG 2.2 AA](https://www.w3.org/WAI/WCAG22/quickref/): клавиатура, видимый focus, labels, контраст, reflow и сообщения ошибок; это рекомендация качества, не уже подтверждённая сертификация.
Статусы различаются текстом/иконкой, а не только цветом. У диаграммы есть название и доступная табличная альтернатива.
Изменения чата объявляются screen reader дозированно, без чтения каждого токена; отправка, отмена и ошибки доступны с клавиатуры.
Готовые MUI-компоненты помогают, но доступность всего сценария проверяется вручную и в браузерных тестах.

## Структура приложения

Предварительная организация (без создания frontend-кода):

```text
frontend/src/
  app/                    # bootstrap, providers, router, theme
  pages/                  # композиция экранов проекта и истории
  features/
    project/              # открытие и выбор проекта
    chat/                 # сообщения, уточнения, запуск операции
    model-editing/        # формы, YAML и диагностика
    proposals/            # diff, принятие, отклонение
    verification/         # формальные отчёты и judge
    artifacts/            # таблицы, диаграммы, экспорт
    history/              # редакции, diff и восстановление
    approvals/            # явное согласование снимка
  shared/
    api/                  # transport, общие ошибки, OpenAPI-типы
    ui/                   # действительно повторяемые компоненты
    lib/                  # небольшие общие функции
```

Внутри фичи рядом находятся компоненты, hooks запросов/команд и тесты; страницы только собирают рабочую область.
`shared` не импортирует features/pages; фичи взаимодействуют через страницы и публичные контракты, без циклических barrel exports.
Типы API рекомендуется генерировать из OpenAPI через openapi-typescript; один transport на fetch обрабатывает ошибки, revision и отмену.
До появления API прототип использует статические синтетические fixtures; после подключения серверные данные не дублируются в константах UI.
Подход к линтерам, component и E2E-тестам описан в [quality-and-testing.md](quality-and-testing.md#frontend).
