# Backend

[Навигация](README.md) · [Контракты агентов](agents.md) · [Конфигурация](configuration.md)

## Стек и границы

Рекомендуется Python backend на FastAPI с асинхронными LLM-вызовами; HTTP API описывается OpenAPI.
Pydantic проверяет внешние контракты, Dishka связывает зависимости, Pydantic Settings собирает настройки.
Предметные классы — обычные dataclasses, enum и явные валидаторы: это сохраняет независимость модели по FR-06.
Полноценные DDD, CQRS, event sourcing и микросервисы здесь не обоснованы: предметных границ и одного процесса достаточно.
Альтернатива FastAPI — Django с ORM и admin; в текущем MVP нет требований, окупающих его дополнительные механизмы.
Python minor и совместимые стабильные выпуски библиотек проверяются вместе при создании каркаса; зависимости фиксируются через uv и lock-файл.

## Выбор LLM-библиотеки

Сравнение относится к библиотекам Python, а не к обязательному запуску LiteLLM Proxy или платформы LangSmith.

| Критерий SolutionArchitectAI | LiteLLM | LangChain |
| --- | --- | --- |
| Разные облачные и локальные LLM | Единый формат сообщений и адаптеры, включая [Ollama](https://docs.litellm.ai/docs/providers/ollama) и OpenAI-совместимые endpoints | Интеграции моделей через отдельные пакеты провайдеров; локальные подключения также доступны |
| Структурированный вывод | [response_format / JSON Schema](https://docs.litellm.ai/docs/completion/json_mode); поддержку проверяем для пары модель/провайдер | [ProviderStrategy / ToolStrategy](https://docs.langchain.com/oss/python/langchain/structured-output), Pydantic и обработка ошибок схемы |
| Инструменты | [Tool calling](https://docs.litellm.ai/docs/completion/function_call) передаёт запрос функции; разрешение и выполнение остаются приложению | Готовые abstractions tools и агентный цикл удобны для большого набора интеграций |
| Специализированные агенты | Роль, инструкции и схема ответа задаются нашими компонентами; последовательность контролирует orchestrator | Готовый агентный runtime сокращает код сложных циклов, но не реализует правила согласования FR-11 |
| Контекст и история | Приложение само отбирает сообщения, источники и лимиты | [Память потока](https://docs.langchain.com/oss/python/langchain/short-term-memory), сокращение сообщений и checkpoint-механизмы |
| Тесты без сети | Fake нашего LLM-порта; [mock_response SDK](https://docs.litellm.ai/docs/completion/mock_requests) для адаптера | Fake модели/инструменты и подмена собственного порта; реальная модель также не обязательна |
| Связанность | SDK изолирован одним infrastructure-адаптером; domain не знает messages или response_format | При прямом использовании AgentState/messages в use cases смена framework дороже; адаптер сохраняет независимость |
| Общий интерфейс агентов | Естественно: собственный контракт над тонким транспортным портом | Возможно за адаптером, но framework-state не должен стать предметной моделью |

Рекомендация: **LiteLLM SDK достаточен** для извлечения требований, вопросов, предложений данных/интеграций и отдельного judge.
Оплата простоты — небольшой собственный код отбора контекста, координации и проверки ответов; он всё равно нужен для инвариантов проекта.
LangChain имеет смысл при доказанной потребности в многочисленных готовых tools/retrievers и сложных агентных циклах.
Совместное использование сейчас удваивает уровни абстракции, политики ошибок и повторов без необходимой функциональной выгоды.
Если такой сценарий появится, LangChain подключается за существующим портом; сочетание требует отдельного измеримого обоснования.
[LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) полезен для ветвящихся длительных процессов с возобновлением и interrupts, но наличие нескольких агентов само по себе его не требует.
Его checkpoint не заменяет Git-редакцию, доменную валидацию и решение архитектора.

Native structured output — помощь в соблюдении схемы, а не доказательство корректности архитектуры.
Для модели без строгой схемы допускается ограниченная попытка JSON с локальной Pydantic-проверкой; неподдерживаемая обязательная capability даёт явную ошибку.
Имена моделей не гарантируют одинаковую поддержку tools, схем, temperature и token-параметров: адаптер проверяет их и не удаляет существенные параметры молча.
Политики ошибок и повторов описаны только в [agents.md](agents.md#ошибки-повторы-и-отмена).

## Слои и Vertical Slice Architecture

Это слоистая архитектура с группировкой по фичам внутри слоёв, без независимого стека библиотек для каждой фичи.
Пример: анализ требований имеет свои предметные правила, use case и HTTP-адаптер, но использует общие порты LLM и истории.

| Слой | Ответственность и допустимые зависимости |
| --- | --- |
| domain | Модели, граф и инварианты; только стандартная библиотека и свои предметные модули |
| application | Use cases, orchestrator, входные/выходные DTO, порты; зависит от domain |
| infrastructure | Реализует порты application, преобразует внешние данные; зависит от application/domain и внешних библиотек |
| presentation | FastAPI и возможный CLI; вызывает application, преобразует API DTO, не импортирует реализации infrastructure |
| config | Чтение источников настроек и проверка при старте; не импортируется domain/use cases |
| di | Composition root: связывает все слои и передаёт типизированные настройки |
| logging | Настройка handlers/формата и redaction; собственная настройка не импортируется domain |

Infrastructure и presentation не зависят друг от друга. DI — единственное место сборки конкретных реализаций.
Межфичевые операции вызывает application-координатор через публичные контракты; HTTP-router одной фичи не вызывает router другой.
Не создаём общий `utils` для несвязанных обязанностей. Общие ID и ошибки выделяются только при фактическом переиспользовании.
Чтобы исключить циклы, контракты принадлежат потребителю: порты хранилища/LLM/рендеринга — application; чистые предметные политики — domain.
Регистрация DI и импорты presentation отсутствуют в этих контрактах; архитектурные проверки импортов входят в [план качества](quality-and-testing.md).

Предварительная структура (только проектирование; каталоги пока не создаются):

```text
backend/
  src/solution_architect_ai/
    domain/
      requirements/       # требования, уточнения, допущения
      architecture/       # системы, данные, потоки, взаимодействия
      verification/       # правила, граф, статусы контроля
      decisions/          # основания и согласования
    application/
      requirements/       # анализ, ответы и предложения изменений
      architecture/       # применение кандидата
      verification/       # формальная проверка и judge
      history/            # сохранение, diff, восстановление
      agents/             # контракты и orchestrator
      ports/              # действительно общие внешние границы
    infrastructure/
      llm/                # адаптер LiteLLM и инструкции
      documents/          # чтение источников и YAML
      persistence/        # Git, файлы, журнал операций
      rendering/          # проекции, PlantUML и SVG
    presentation/
      http/               # routers и API DTO по фичам
      cli/                # только при необходимости
    config/               # Settings и загрузка
    di/                   # bootstrap и небольшие providers
    logging/              # настройка журналирования
```

Pydantic API DTO находятся в presentation и не передаются в domain.
Application DTO — dataclasses с семантикой use case, не копии HTTP Request/Response; Pydantic LLM/YAML-схемы принадлежат соответствующим адаптерам.
Разделение оправдано уже различием русских YAML-ключей, JSON-контрактов LLM и устойчивых доменных ID; не нужен DTO для каждой внутренней передачи значения.
Внешние неизвестные поля и неверные типы отклоняются, затем mapper создаёт предметного кандидата и запускает общие валидаторы.

## Dishka и точки входа

Выбираем [AsyncContainer и интеграцию FastAPI](https://dishka.readthedocs.io/en/stable/integrations/fastapi.html).
`di/bootstrap` только собирает список providers; отдельные providers конфигурации, LLM, хранения, requirements и verification регистрируют небольшие группы зависимостей.
Providers группируются по фиче, а общие внешние ресурсы — по интеграции. Не создаём параллельный контейнер FastAPI Depends для тех же use cases.

| Scope | Примеры и время жизни |
| --- | --- |
| APP | Неизменяемые Settings, клиенты, фабрики репозиториев, реестр агентов; закрываются при shutdown |
| REQUEST | Use case, контекст операции и доступ к проекту; завершаются после HTTP-запроса |
| Отдельный execution scope | Orchestrator длительного запуска получает свой дочерний scope; не удерживает закрытый HTTP REQUEST |

APP-объект не захватывает REQUEST-зависимость. Выбор project_id не хранится в глобальном singleton.
CLI при необходимости создаёт тот же composition root и scope операции, затем вызывает use case без HTTP.
В unit-тестах use cases собираются напрямую с fake-портами; integration-тест отдельно проверяет граф DI и cleanup.
Router выполняет разбор DTO, вызов одного use case и перевод результата/ошибки в HTTP; в нём нет решения о применимости стандарта.

## Предметная модель, ввод и артефакты

Предлагаемый первый импорт — UTF-8 Markdown/текст с сохранением исходника, хеша и позиций фрагментов; манифест — YAML.
PDF/DOCX через Docling — альтернатива при требовании этих форматов, после проверки цитирования и извлечения на синтетике; Confluence отложен.
Для YAML рекомендуем [ruamel.yaml](https://yaml.dev/doc/ruamel.yaml/api/): отклонение дубликатов, безопасное чтение и координаты узлов для диагностики.
PyYAML проще как распространённая альтернатива, но потребует отдельного контроля дублирующихся ключей и сопоставления ошибок с текстом.
Разбор не конструирует произвольные Python-объекты; размеры, глубина, aliases и неподдерживаемые tags ограничены на границе.
При импорте профили эталона разворачиваются до построения domain: неизвестные и вложенные профили отклоняются, локальные поля имеют приоритет, вложенное происхождение разворачивается отдельно.
Сохраняется карта «доменное поле → место YAML», чтобы ошибка ссылки показывала строку/поле исходного ввода.

Служебный ID назначает приложение; осмысленный YAML-ключ — внешний alias. Его переименование выполняется операцией с обновлением ссылок, не заменой строк.
Неверный YAML/JSON/UI-кандидат остаётся черновиком; валидаторы одни для всех трёх способов ввода.
Стадия определяет обязательность сведений: незавершённость явно отмечается; отсутствие обязательного условия не получает результат «пройдено».
Графовые проверки — направленные списки смежности, обходы достижимости и явные правила ролей, без графовой БД и пока без NetworkX.
Проверяются ответы, Access read/write, целевые типы ссылок и профиль VIEW-01; источник/хранилище/конечный получатель не объявляется дефектом из-за одной отсутствующей стороны.
SEC-01–SEC-08 из примера — версионируемые входные правила, а не захардкоженная политика для всех проектов.

Для формализованных правил рекомендуем небольшой реестр готовых чистых Python-валидаторов по виду проверки, а не по ID корпоративного документа.
Версионируемая привязка содержит источник/редакцию, вид проверки, типизированные параметры, область, обязательность, условия применимости и допустимые исключения.
Например, требование TLS связывается с проверкой защиты подходящих взаимодействий, а выбор прокси — с проверкой маршрута и профиля обслуживания.
Человек подтверждает формализацию и применимость; LLM может предложить привязку, но не включить её самостоятельно. Python, eval и универсальный DSL из текста стандарта не исполняются.
Неподдерживаемое или неоднозначное правило остаётся «не проверено»; обязательное условие блокирует согласование до формализации либо явной проверки/подтверждения человеком с основанием.
Новый вид валидатора добавляется обычным кодовым PR с положительными/отрицательными примерами; изменение binding или версии валидатора инвалидирует соответствующие проверки.

Таблицы, YAML и модели двух диаграмм — детерминированные проекции одной domain-редакции; A-01/A-07 и согласования не запихиваются целиком в A-06.
PlantUML генерируется шаблонами из проверенных проекций; текст LLM не исполняется как .puml.
Адаптер запускает локальный PlantUML CLI, формирует .puml и SVG и записывает профиль/версии рендерера; экспорт Archi зависит от Q-03.
Повторный рендер без ИИ сохраняет семантику, а не обязательно байты SVG; ошибка рендера оставляет предыдущий комплект и диагностику, не объявляет новый экспорт готовым.

## Хранение и запись в Git

Рекомендуется файловое хранилище и отдельный локальный Git-репозиторий на проект с одной основной веткой.
SQLite/PostgreSQL пока не нужны: FR-11 уже требует снимки Git, а параллельная БД создала бы вторую авторитетную копию модели.
Tracked snapshot содержит исходники/контекст, модель, A-01–A-07, проверки и решения; untracked-каталоги рядом с репозиторием — черновики, chat/run-state и журнал незавершённых операций.
Файлы run-state записываются атомарной заменой; данные между рестартами сохраняются на томе. Диалог не используется для восстановления domain вместо снимка.

Запись сериализуется блокировкой проекта, действующей и для HTTP, и для CLI; чтения используют неизменяемые снимки.
Use case сверяет ожидаемый HEAD, готовит полный снимок во временной области, затем создаёт Git tree/commit и обновляет ref через compare-and-swap.
Только успешное обновление ref публикует новую сохранённую редакцию; читатели не читают частично изменённый working tree.
В снимке записаны operation_id и автор/причина; pending-журнал вне Git содержит ожидаемый parent и подготовленный commit.
При повторе сначала проверяются ключ идемпотентности и хеш payload: сохранённый результат возвращается до сравнения expected_commit; проверка HEAD выполняется только для новой операции.
Сбой до публикации оставляет pending/черновик и прежний HEAD; сбой после публикации, но до ответа восстанавливает результат по operation_id в истории без повторного коммита.
При старте незавершённая операция сверяется с HEAD/историей; недописанные файлы не принимаются за актуальный снимок. Публикация блокируется при необъяснимом расхождении.
При ошибке Git пользователь видит несохранённое действие и может безопасно повторить его; подтверждение не выдаётся до успешной записи.

Проверки ссылаются на хеши содержимого модели, источников, правил и версию валидаторов; перед согласованием они должны соответствовать одному полному снимку H.
При необходимости отчёт записывается отдельным коммитом без изменения проверенных входов; согласуемый H уже включает оба результата проверок и артефакты.
Коммит согласования добавляет только запись «кто/когда/область/полный H», не меняя согласуемые артефакты; собственный будущий hash в него не записывается.
Смена требований/правил сохраняется коммитом и снимает актуальность зависимых проверок/согласований; прежняя модель остаётся доступной, её нарушения относительно новых правил показываются явно.
Это не применение невалидного предложения модели: исправляющий кандидат проходит актуальные валидаторы отдельно.
Восстановление создаёт новый коммит со ссылкой на исходный hash, проверяет восстановленную модель по текущим правилам и сохраняет прежнее согласование только как историческое свидетельство.

## Выполнение и диагностика

Для MVP — один backend process/worker, ограниченные in-process задачи и персистентный run-state; после рестарта незавершённый LLM-вызов помечается interrupted, автоматическое повторное применение запрещено.
HTTP-команда запуска возвращает run_id, интерфейс опрашивает статус; SSE можно добавить при необходимости потокового чата, WebSocket пока не требуется.
Синхронные Git/файловые операции и запуск рендерера выносятся из event loop; см. [правила async FastAPI](https://fastapi.tiangolo.com/async/).
Стандартный logging со структурированным JSON содержит project_id, run_id, operation_id, длительность, тип ошибки и usage LLM.
Ключи, исходные документы и полный prompt по умолчанию не попадают в эксплуатационные логи; материалы воспроизведения хранятся отдельно согласно [контракту агентов](agents.md).
Число процессов, очередь задач и сроки хранения — точки пересмотра при изменении требований, а не скрытые обещания распределённой надёжности MVP.
