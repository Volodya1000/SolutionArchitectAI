# Backend и хранение

[Навигация](README.md) · [Агенты](agents.md) · [Качество](quality-and-testing.md)

## Стек и направления зависимостей

Рекомендуется модульный Python backend: FastAPI/OpenAPI, Dishka AsyncContainer, PostgreSQL, SQLAlchemy 2.x async и Alembic. Pydantic проверяет внешние контракты, Pydantic Settings — конфигурацию. Domain использует dataclasses/enum и чистые валидаторы без ORM/HTTP/LLM SDK. Полные DDD, CQRS, event sourcing и микросервисы MVP не нужны. Фичи группируются внутри пакетов; общие порты принадлежат их потребителю в Application.

| Пакет | Обязанность и допустимые импорты |
| --- | --- |
| domain | Архитектурные объекты, требования, решения и инварианты; стандартная библиотека и свой код |
| application | Use cases, агентные DTO и Pydantic-схемы результатов, ContextBuilder, pipeline, порты; зависит от domain, не от адаптеров |
| persistence | SQLAlchemy, Alembic, SQL-репозитории, Git-адаптер, local/S3 storage; реализует порты application, может использовать domain |
| infrastructure | LiteLLM/Instructor, парсеры документов, PlantUML; реализует порты application |
| presentation | FastAPI, HTTP DTO, SSE и возможный CLI; вызывает application, не конкретные persistence/infrastructure |
| config | Чтение и валидация настроек; не импортируется domain/application |
| di | Composition root связывает реализации и lifecycle; единственная точка сборки |

**Persistence — отдельный технический пакет инфраструктурных адаптеров, а не новый внутренний архитектурный слой.** Зависимости направлены внутрь к Application/Domain. Infrastructure, Persistence и Presentation независимы друг от друга. Не вводим Domain → Persistence или универсальный `IRepository`, скрывающий различия SQL и Git.

```text
backend/src/solution_architect_ai/
  domain/                 # architecture, requirements, decisions, verification
  application/            # use cases по фичам, agents, context, ports
    prompts/              # один промпт — один Python-файл
  persistence/            # postgres, migrations, git, files
  infrastructure/         # llm, documents, rendering
  presentation/           # http, streaming
  config/
  di/
```

Application DTO выражают команду/результат, а не копируют HTTP-объекты. Общие Pydantic-схемы LLM принадлежат Application, SDK-типы не выходят из Infrastructure. Mapping в domain явный; неизвестные поля внешних контрактов отклоняются.

Dishka APP scope владеет пулами/HTTP-клиентами и фабриками; REQUEST — коротким use case и SQL session. Длительный run получает отдельный execution scope и не удерживает HTTP session. APP не захватывает REQUEST. При shutdown ресурсы закрываются. Unit use cases собираются напрямую с fake-портами; integration проверяет DI/lifecycle.

## Предметная модель и представления

Один репозиторий на корпоративное пространство: каталоги систем, компонентов, данных, интерфейсов, отношений, интеграций, решений и оснований. Проекты/задачи выбирают ID общего каталога. Повторное использование не создаёт копию; одноимённые объекты не объединяются автоматически без проверки идентичности человеком.

`View` имеет устойчивый ID, folder_id, viewpoint/profile и ссылки на общие объекты/отношения. `ViewNode` имеет свой ID и object_id; `ViewEdge` — relationship_id и ссылки на визуальные узлы. Позиции, scale, группировки, label override и style принадлежат виду. Отношение имеет собственные концы и свойства; визуальная линия не меняет его семантику. Изменение общего имени обновляет все виды, кроме явно заданной локальной подписи; UI показывает наличие override. Поиск «где используется» вычисляется по ссылкам.

При удалении общего объекта сначала показывается влияние на отношения и виды; висячие ссылки запрещены. Удаление из одного вида сохраняет каталог. После изменения общего объекта пересоздаются зависимые проекции, сбрасывается актуальность проверок; layout других видов сохраняется. Графовые проверки выполняются на заявленном срезе, не требуют соединить весь корпоративный каталог.

Хранение — **JSON**, не YAML и не XML. Рекомендуемая раскладка: `model.json` со schema_version и ID пространства, `objects/<id>.json`, `relationships/<id>.json`, `views/<id>.json`, `view-tree.json`, `decisions/<id>.json`, `sources/<id>.json`, `checks/`. Несколько файлов уменьшают конфликтность diff. UUID назначает приложение; имена и aliases можно менять без смены ID. Schema version имеет явные миграции; неизвестная версия отклоняется, исходный снимок сохраняется.

UTF-8, фиксированные отступы и newline, сортировка ключей; множества сортируются по ID, последовательности (порядок узлов дерева/точек линии) сохраняют смысловой порядок. В модель не добавляются плавающие timestamps ради сериализации. Одинаковые входы и версия сериализатора дают одинаковый JSON. Duplicate JSON keys отклоняются стандартным decoder hook, не скрываются последним значением. JSON Schema проверяет форму; независимые domain-валидаторы — ссылки, типы концов, ограничения и правила. UI и LLM-кандидаты проходят те же валидаторы. Обычный пользователь не редактирует JSON вручную.

Таблицы A-01–A-07, .puml и SVG — проекции одной редакции, не независимые модели. Рендерер получает проверенный срез и профиль; исходный LLM-текст не исполняется как PlantUML. Без LLM повторный рендер сохраняет смысл и ID. Ошибка рендера оставляет предыдущий экспорт с явной старой редакцией. Направление данных, инициатор вызова, ответ и Access read/write хранятся отдельно. Exchange XML рассматривается отдельно после решения по экспорту в Archi.

Markdown/текст — первый документный вход с оригиналом, SHA-256 и локаторами фрагментов. PDF/DOCX/Docling оцениваются на цитируемость при расширении набора. Формализация правил — подтверждаемая человеком привязка версионируемого источника к виду чистого валидатора и типизированным параметрам, области и исключениям. ИИ не исполняет текст правила как Python/eval/DSL. Неизвестная обязательная проверка остаётся «не проверено», а не «пройдено».

## Распределение данных и порты

| Хранилище | Авторитетные данные | Порт Application |
| --- | --- | --- |
| Git | JSON-модель, дерево видов, существенные подтверждённые решения, версионируемые результаты проверок, pinned источники, воспроизводимые .puml | ArchitectureRepository: read_revision, create_task_branch, commit_changes(expected_head, operation_id), diff, inspect_merge |
| PostgreSQL | Пространства/проекты/задачи, чаты/сообщения, agent runs, drafts/proposals, ответы, настройки, статусы, привязки веток/коммитов, журнал операций и разрешений | TaskRepository, ChatRepository, RunRepository, OperationJournal и SQL UnitOfWork для одной БД |
| Local filesystem или S3-compatible API | Оригиналы документов/вложения, крупные бинарные файлы, производные и временные экспорты | FileStorage: put_immutable, get_version, verify, delete_unreferenced |

Git и SQLAlchemy не взаимозаменяемы. Будущий GitLab-адаптер добавит удалённые операции к Git-порту без изменения domain; MR не часть обязательного workflow. Права на merge остаются у человека вне LLM-порта. История сообщений не служит реестром подтверждённых решений: существенный ответ переносится в model/decision отдельной командой человека.

Файловая запись в PostgreSQL содержит file_id, version_id, SHA-256, MIME type, size, owner/access scope, storage_key и ссылки message/source. Версия immutable: новый upload — новая версия/ключ, а не overwrite старого. Git pin содержит file_id/version_id/hash и точный локатор; доступ проверяется по корпоративной области. Для исходников, включённых в репозиторий примера, допустимы путь и SHA-256 содержимого. Hash не заменяет проверку доступа.

До публикации commit проверяются существование и хеш всех обязательных версий. Referenced sources удерживаются retention pin, физическое удаление запрещено пока на них ссылается сохраняемая история/согласованная модель; garbage collection сверяет Git и PostgreSQL. Смена активной версии не ломает старую ссылку. Если источник недоступен, это диагностируется как потеря воспроизводимости; не заменяем его текущим документом молча. Политика хранения/backup должна охватывать все три хранилища.

## Git workflow

1. `main` — согласованная модель. CreateTask фиксирует полный M = текущий main и создаёт `task/<task-id>` именно от M; смена main при создании требует повторной проверки актуальности до продолжения.
2. ИИ создаёт proposal в PostgreSQL, привязанный к head H, источникам и правилам. Не пишет в Git. Принятие человеком запускает построение/валидацию кандидата, пересчёт зависимых видов и commit в ветке через compare-and-swap ref H → H1. В commit metadata: operation_id, автор, причина.
3. Формальные и отдельные смысловые проверки закреплены за digest архитектуры/источников/правил/рендерера. Reports можно сохранить следующим commit без изменения проверенных входов. Недостаточно данных/обязательная ошибка блокируют согласование.
4. Человек согласует точный head H, tree T, область и актуальный M; разрешение хранится с operation_id в PostgreSQL. Подтверждённые предметные решения уже находятся в H; новое решение меняет H и требует нового согласования. Коммит сам по себе не approval.
5. Merge выполняет уполномоченный человек обычными средствами Git. Перед ним нужны актуальность main, отсутствие конфликтов, checks, source pins, анализ влияния общих объектов, ReviewReport и разрешение на точное содержимое. Автоматический merge от ИИ запрещён.
6. Предпочтителен fast-forward при неизменном M. Для merge commit результат должен иметь согласованный tree T и ожидаемых родителей; если содержание отличается, требуется новая проверка/согласование. Приложение регистрирует M/H/T, actor, approval и фактический merge hash, проверяет ancestry/tree. Необъяснимый внешний merge помечается как требующий сверки, не как согласованный автоматически. После успешной сверки task закрывается; удаление ветки — по политике, commit и источники удерживаются.

Если main изменился, обновление рабочей ветки выполняется явной Git-операцией человека (merge/rebase по политике), с повторными проверками. Любой новый head инвалидирует прежнее разрешение; rebased commit имеет новый hash. Конфликты показываются по объектам/файлам, сложного автоматического разрешения нет. Даже чистый Git merge может содержать смысловой конфликт двух изменений общего объекта: это проверяется заново. Для MVP допустим последовательный порядок интеграции задач.

Rollback/revert — новое изменение в рабочей ветке с актуальными правилами и новым approval, без rewrite main. Все writers используют блокировку repo/ветки и expected ref; внешние Git-изменения также проверяются CAS. Read API читает immutable commit, не частично изменённый working tree.

## Согласованность хранилищ

Общей транзакции PostgreSQL/Git/S3 нет. Одна команда имеет operation_id, scope, payload digest, expected_head и журнал стадий. SQL UoW обеспечивает атомарность только собственных записей.

| Стадия | Действие и восстановление |
| --- | --- |
| prepared | SQL фиксирует intent и ключ идемпотентности; повтор с другим payload отклоняется; повтор завершённого результата возвращается до проверки текущего HEAD |
| files_ready | immutable upload по заранее назначенным version/key; verify size/hash; pin/reservation. Сбой оставляет pending объект, повтор проверяет существующий, не перезаписывает |
| git_prepared | кандидат проверен, commit создан, hash записан в журнал; неизменяемая staging ref удерживает commit до recovery |
| git_published | CAS обновляет task ref; operation_id находится в metadata. Сбой до CAS оставляет прежний head; после CAS результат восстанавливается по commit/ref и журналу, без второго commit |
| completed | SQL сохраняет итоговый hash, связи и pin; ответ выдаётся после сверки. Если SQL недоступен после CAS, операция pending/recovering, а не откатившаяся |

Сбой между созданием commit и записью его hash восстанавливается по operation_id/staging ref. Recovery проверяет ожидаемого родителя и payload digest; при внешнем продвижении ref ищет результат в истории, неоднозначность блокирует новую запись. Короткая публикация защищена от отмены HTTP; disconnect не отменяет уже применённое действие. GET operation_id сообщает фактический исход. Cleanup не удаляет данные pending/published операций; при недоступном хранилище GC приостанавливается. Слепой retry всей команды недопустим.

## Асинхронное выполнение и диагностика

Один backend worker для MVP и ограниченные управляемые задачи; PostgreSQL хранит run-state после рестарта. Стадии claim выполняются атомарно с версией/lease, чтобы два возобновления не породили две публикации. Redis/workflow engine не нужны. LLM-вызов не держит DB-транзакцию или Git lock.

Async оправдан для LLM, HTTP, SQL async driver, streaming и поддерживаемого storage I/O. Синхронный Git/локальные файлы выносятся в контролируемый thread pool; CPU-парсинг и тяжёлый рендер — в process/subprocess с timeout и cleanup. Чистые domain-правила остаются синхронными. Не блокируем event loop, не делим одну AsyncSession между конкурентными задачами; session на отдельный use case/task ([SQLAlchemy](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#using-asyncsession-with-concurrent-tasks)).

TaskGroup/структурированная конкурентность там, где подзадачи имеют общий lifecycle; нет бесконтрольных fire-and-forget. CancelledError распространяется после cleanup; общий monotonic deadline охватывает ожидание semaphore, сеть, backoff и генерацию. LLM concurrency ограничен. Shutdown прекращает новые runs, отменяет/ожидает активные, закрывает потоки/clients/sessions; незавершённые стадии получают interrupted. Временные и постоянные ошибки различаются.

Команда запуска возвращает run_id. Streaming — SSE (или fetch-stream с согласованным event envelope): run_id, event_id/sequence, kind, payload; reconnect восстанавливает сообщение и статус из PostgreSQL, не запускает новую генерацию. Отмена — отдельная идемпотентная команда; частичный текст остаётся явно incomplete. Логи содержат task/run/operation IDs, задержки, токены, модель/версию, параметры, ошибки и повторы; секреты и полные документы по умолчанию исключены. Расчётов оплаты LLM нет.
