# PR 20: реальная Qwen, 28 ноября 2026

**Модельная приёмка этапа 3 не пройдена.** Ни fake, ни управляемый ответ модели
не подставлялись в эти запуски. [Фактические сообщения, результаты и счётчики](pr20-real-qwen-2026-11-28.json)
содержат только публичные синтетические документы, без ключей и пользовательских
путей. Служебные UUID в отчёте принадлежат тестовым данным приложения.

## Стенд и параметры

LM Studio, `qwen2.5-coder-14b-instruct`, Q4_K_M. Загружена существующая локальная
модель, GPU; context 12288, output 6912, temperature 0.2, concurrency 1,
`native_json_schema`, service tokens 256, approximate chars/token 2.
Network retries 1, validation retries 2, общий max requests 128, active deadline
3600 с, request timeout 600 с, backoff 0.25→2 с, jitter 0.1.
Платных внешних вызовов нет. Параметры между шестью входами не менялись.

Штатный Linux Compose runtime имеет отдельные PostgreSQL/file/Git volumes.
Локальный наблюдающий proxy пересылает тела запросов и ответов без изменения
в LM Studio. URL proxy обезличен в JSON; HTTP остаётся OpenAI-совместимым.
Для каждого входа выбрана ровно одна версия, `answer_history_mode=new`;
history_id/thread_id совпадают с самостоятельным run_id, перечисленным в JSON.

Фазы: `extract-3`, `requirements-1`, `clarify-4`, `clarification-1`,
`clarify-review-1`, `conflict-assessment-1`, `structured-3`, `source-aliases-1`.
В фактически отправленных системных сообщениях структурированных фаз кириллицы
нет; исходный русский документ и цитаты передаются без перевода. Предметный чат
сохраняет общую русскую инструкцию обычного диалога отдельно от structured phases.
Восемь перехваченных первичных payload извлечения дополнительно сформированы
из исходных документов текущим кодом: сообщения совпали для всех восьми окон.
Это проверка соответствия перехвата итоговым сообщениям, а не новые LLM-вызовы.
После финального развёртывания побайтово сверены все 183 Python-файла backend
в Qwen-контейнере с текущим исходным кодом; относительные пути и SHA-256 в JSON.

Начальная команда модели: `lms load qwen2.5-coder-14b-instruct --context-length
12288 --gpu max --parallel 1 --identifier qwen2.5-coder-14b-instruct --yes`;
затем `lms server start --port 1234 --bind 127.0.0.1`.
Первоначально endpoint отвечал connection refused; после запуска доступен.
Попытка native Windows backend прервалась до приёмки. Приведённые ниже
результаты получены через отдельный Compose, а не тем остановившимся процессом.

Отложенные пары находятся в `docs/examples/pr3/heldout-window-*.md` и
`heldout-period-*.md`. У них другие предметы, формулировки и сроки; идентификаторов
R-03/R-04 нет. Production-код и промпты не содержат этих ID, имени BRD или
ожидаемого ответа.

На полном английском входе фактический вопрос:
«What is the specific policy for handling export data beyond the six-week retention period?».
`blocking=true`, basis=`f1`, dependent_decision=`r4`, ссылка на требование срока
хранения. Перепроверка вернула `resolved=false`: она увидела явный отказ запросу
вне интервала, но трактовала вопрос как отдельную политику хранения после срока.
Это ложная блокировка и недостаточная содержательность dependent_decision.

На неполном английском входе вопрос:
«What is the policy for retaining export data beyond six weeks?»;
dependent_decision=`determine_long_term_storage_needs`, `blocking=true`.
Перепроверка также вернула false. Подтверждённая цитата в обоих случаях —
«The service retains export data for six weeks after ingestion.».
Нужный вопрос о поведении при недопустимой дате не найден.

Локализация: в английской паре первичное извлечение сохранило условие интервала,
а полный вариант передал также явный отказ. Информация присутствует в реальном
ClarificationSet payload. Ошибка возникает при выборе вопроса самим агентом;
следующий SourceReviewVerdict сохраняет ошибочный предмет вопроса. Данные не
исчезают в серверном объединении или фильтрации. В русских BRD отказ происходит
раньше, при проверке языка нормализации; полное покрытие не объявляется.

Общая диагностика языка ранее терялась в `value_error`. На новых запросах
подтверждён путь `requirements.0.normalized_text` и безопасная причина «preserve
the Cyrillic source language ...». Это исправляет обратную связь, но не
гарантирует послушание модели: ограничения языка и обрезки не ослаблялись.

## Предметный чат и restart

Через видимое «Обсудить» у фрагмента R-04 неполного BRD задано:
«Срок хранения уже указан. Что именно нужно уточнить?».
`discussion-3` ответил, что срок известен и уточнений не требуется. Ссылка R-03
построена сервером из короткой метки и открывает строку 19 закреплённой версии.
Ссылка R-04 в этом ответе отсутствует; недостающее поведение не объяснено.

PostgreSQL перезапущен с сохранением volumes, backend/frontend пересобраны
на текущем коде. Тот же чат `8bab1b8b-ba3e-472d-9858-aa4c18f2fa03` сохранил
сообщения и закреплённую версию. `discussion-4` добавляет общее правило различать
ограничение и поведение при его нарушении; повтор в прежнем чате снова не назвал
пропуск. Переход по R-03 после restart проверен в браузере, точная исходная строка
осталась доступна; анализ и история сохранились.
После restart прямое чтение PostgreSQL подтвердило прежние thread_id обоих
больших BRD: у каждого осталось по четыре строки `checkpoints`.

Отдельно через видимую строку требования R-04 открыт новый предметный чат
`c263cced-8b92-48e4-96df-64e0203edc7b`, без прежнего ответа в истории.
На `discussion-4` Qwen перечислила известные факты и снова заявила, что всё задано.
Она выдала работающие серверные ссылки на выбранное требование R-04, но не R-03.
Переход R-04 открыл выбранную строку с фокусом в видимой области; переход от неё
к источнику открыл исходную строку 20 прежней версии и сохранил run.
Фактические payload обоих режимов содержат короткие ссылки вместо UUID/SHA,
а приложение хранит полные идентификаторы и исходные цитаты.

В этих BRD вопросы не были созданы из-за отказа извлечения. Поэтому проверить
«свободный диалог оставляет реальный вопрос открытым → один ответ через карточку →
тот же thread → продолжение» на реальной модели **не удалось**. Вопрос не внедрялся
в БД и ответ не подставлялся. Соответствующий fake desktop-сценарий выделен
в основном отчёте и не закрывает этот критерий.

## Воспроизведение и незакрытый критерий

```powershell
uv run --locked --project backend python -m tools.clarification_smoke `
  --base-url http://127.0.0.1:32806 `
  --source docs/examples/pr3/reporting-system-complete.md `
  --output .build/qwen-complete-final.json --timeout 3600
```

Для неполного BRD используется `reporting-system-incomplete.md`, для контрольных
пар — четыре `heldout-*.md`; каждое отдельное исполнение создаёт новую историю.
Адрес относится только к этому локальному стенду; профиль выше обязателен для
сравнения. Наблюдающий proxy и сырые рабочие журналы лежат в ignored `.build`;
обезличенные фактические тела всех предметных вызовов включены в JSON отчёта.

Открыты: успешное извлечение обоих больших русских BRD; правильный вопрос
неполного документа; отсутствие ложной блокировки полного; содержательный
предметный ответ с обеими ссылками; сохранение одного настоящего ответа после
restart и resume на Qwen. Старый запуск `clarify-3` эти критерии не закрывает.
