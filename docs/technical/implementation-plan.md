# План следующих небольших PR

[Навигация](README.md) · [Исходные требования](../BRD.md) · [Открытые согласования](../review.md)

Цель — перейти от технического предложения к проверяемому приложению, сохраняя небольшие предметные шаги.
Это последовательность PR с результатами и критериями готовности, а не детальная спецификация всех классов/методов MVP.
Каждый PR отдельно ревьюится и не сливается автоматически; текущий PR содержит только техническую документацию и ссылку из README.
До продуктового кода требования и ручной эталон согласуются по review.md; слияние этого технического PR не подменяет решение архитектора.
Версии, числовые параметры и уточнения, не закреплённые BRD, остаются рекомендациями до соответствующего ревью.

## PR 1. Статический прототип рабочего места

Цель: согласовать Q-02 и понятность пользовательских действий до реализации предметной логики; это следующий PR после текущего.
Результат: отдельный статический HTML/React-прототип на синтетике с чатом, областью проекта, предложением/diff, артефактами, проверками и историей.
Можно использовать минимальный Vite preview, но нет LLM, backend use cases и настоящих согласований/сохранений.

Критерии готовности:

- Различимы «черновик», «предложение ИИ», «применено», «сохранено» и «согласовано»; видны основания и два вида проверок.
- Показаны блокирующее уточнение, ошибка YAML и конфликт редакции; пользовательский сценарий не требует ввода служебных ID.
- Прототип читаем на узком/широком экране и доступен с клавиатуры; стороны явно фиксируют замечания и решение по интерфейсу.
- Синтетические данные подписаны как демонстрационные; макет не объявляется реализацией AC-01–AC-17.

Вопросы к этому ревью: интерфейс Q-02, обязательность Archi Q-03 и достаточность манифеста Q-04; открытое решение не закрывается молча макетом.

## PR 2. Исполняемый каркас, инструменты и локальный запуск

Цель: закрепить структуру двух приложений и короткий воспроизводимый цикл разработки.
Результат: backend/frontend packages по [проектированию](backend.md), composition root Dishka, FastAPI health API, SPA shell, настройки и минимальный Compose.
Инструменты качества объединены с каркасом: выделять отдельный «пустой PR линтеров» не требуется.

Критерии готовности:

- Выбраны совместимые стабильные Python/Node и зависимости; uv/npm lock-файлы, одна documented команда установки/запуска и checks.
- Конфигурация соответствует [приоритетам](configuration.md): безопасные example, ignore секретов, явный production mode, проверки неверных значений/источников.
- Ruff/Pyright/WPS231 и ESLint/Prettier/tsc работают без дублирующего шума; CI запускает имеющиеся meaningful проверки, не добавляет заглушки тестов ради зелёного отчёта.
- Контейнеры стартуют, readiness и `/api` proxy работают; после пересоздания backend сохраняется volume; LLM/внешние ключи не требуются.
- DI graph/lifecycle проверен, domain/application не зависят от HTTP/SDK; приложение ещё не объявляется проектирующим архитектуру.

## PR 3. Предметная модель и первый вертикальный сценарий без LLM

Цель: получить наблюдаемый путь «ввод → валидация → сохранённая редакция» на маленьком срезе архитектуры.
Результат: устойчивые ID, модели систем/данных/потоков, provenance и начальные A-01/A-06/A-07; импорт YAML через общие валидаторы и минимальный UI.
Остальные стадии остаются явно незавершёнными, не создаются фиктивные результаты проверок.

Критерии готовности:

- На срезе [эталона](../examples/reporting-system/manifest.yaml) проверены профили, обязательные поля, дубликаты, типы и ссылки с понятной диагностикой.
- Неверный ввод сохраняется черновиком, последняя корректная модель остаётся; то же правило работает через JSON/UI.
- Первое сохранение и каждое применённое изменение дают Git-коммит с автором/причиной; повтор операции не создаёт дубль, ошибка Git не выдаёт успех.
- Unit и real-Git integration защищают результат после рестарта; UI показывает сохранённый hash и несохранённую правку раздельно.

## PR 4. Первый агент: анализ требований и уточнения

Цель: внедрить FR-01/FR-02 через один полностью контролируемый LLM-сценарий.
Результат: LiteLLM-адаптер, единый контракт, orchestrator, Context builder, чат и применение proposal по [agents.md](agents.md).
Смысловой judge добавляется в PR 6; до него этап не объявляется полностью верифицированным/согласованным по FR-10.

Критерии готовности:

- Markdown/текст и синтетический контекст дают A-01 с реальными цитатами/позициями; поддерживаемые форматы явно перечислены.
- Блокирующий вопрос останавливает зависимый переход; допущение атомарно связывает A-01 и риск A-07, не отменяет стандарт.
- Предложение не меняет модель без команды; stale base, timeout/отмена, ошибочный JSON и повторы не заменяют подтверждённые решения.
- Fake LLM покрывает обычный CI; отдельный ограниченный smoke выполняется на выбранной облачной/локальной модели с фиксацией параметров и стоимости.

## PR 5. Архитектура данных, взаимодействия и артефакты

Цель: расширить существующий механизм на FR-03–FR-05/FR-08 без нового агентного framework.
Результат: роли проектирования данных/интеграций с обоснованиями, общая модель и обе проекции, A-02–A-05, полный A-06 и накопленный A-07.

Критерии готовности:

- Потоки данных, инициаторы вызовов, ответы и Access read/write различимы на reporting-system; неиспользуемые активы каталога не считаются изолированными узлами среза.
- Реализованы графовые/формальные проверки AC-12, версионируемые правила и объяснимые статусы FR-09; unsupported проверка не выдаёт «пройдено».
- Привязки правил к реестру валидаторов типизированы и подтверждаются человеком; неизвестное обязательное правило остаётся открытым, текст стандарта не исполняется.
- .puml/SVG формируются локально без LLM; повтор сохраняет семантику, кириллицу и профиль; ошибка рендера не объявляет готовность нового комплекта.
- Архитектор видит альтернативу/основание до принятия; правки не теряются при повторной генерации, поддерживается работа без корпоративного контекста.
- Если объём двух стадий мешает предметному ревью, PR делится на данные и взаимодействия по тем же критериям, без новой архитектуры.

## PR 6. Judge, согласование и полная история

Цель: завершить FR-07/FR-09–FR-11 как согласованный сквозной процесс.
Результат: отдельный ReviewReport, решение человека, согласование точного снимка, текстовый diff, восстановление и инвалидирование зависимых согласований.

Критерии готовности:

- Формальные проверки предшествуют judge; результаты разделены, обязательный дефект/непроверенное условие блокирует согласование.
- В согласуемом снимке присутствуют оба отчёта и комплект; следующий approval-коммит указывает полный hash и не меняет согласуемые артефакты.
- История показывает автора, время, причину и diff; восстановление создаёт новый коммит и проверяет текущие правила, старый approval не становится актуальным автоматически.
- Смена HTTP→HTTPS, SEC-05–SEC-08 и сбой записи воспроизведены по [сценариям](../verification-scenarios.md); interrupted runs восстанавливаются без двойного применения.
- Короткий Playwright-тест проходит весь путь с fake LLM и настоящим backend/Git; готовность функций не выводится из наличия элементов UI.

## PR 7. Измерение качества и приёмка синтетического MVP

Цель: получить доказательства AC-01–AC-17 и определить дальнейшие ограничения качества ИИ.
Результат: согласованный размеченный набор и отчёт воспроизводимых испытаний по [quality-and-testing.md](quality-and-testing.md#llm-без-обязательного-внешнего-api).
Испытания готовятся постепенно в PR 3–6, а не откладываются целиком до этого этапа.

Критерии готовности:

- Набор соответствует минимумам BRD, метрики содержат числители/знаменатели и редакции; fake и реальные LLM-испытания явно разделены.
- Все внесённые формальные дефекты найдены, законные контроли не блокируются; цели смысловой диагностики/генерации предложены по экспериментам, не выдуманы заранее.
- Проверены полный комплект, правки/согласования/восстановление и локальный запуск на чистом data volume; инструкция воспроизведения не требует закрытой инфраструктуры.
- Решение по Q-03 принято до окончательной приёмки: если Archi обязателен, отдельным небольшим PR выполнены XML-экспорт и реальный тест импорта; .puml не выдаётся за обмен моделями.
- Реальные данные/удалённый доступ допускаются только после согласованных требований к защите; испытания синтетики не объявляются доказательством такой готовности.

PDF/DOCX, внешние коннекторы, распределённые задачи и многопользовательская работа добавляются только после изменения согласованного объёма.
Перед каждым PR уточняются затрагиваемые контракты и риски, но не перепроектируются уже принятые границы без обнаруженной необходимости.
