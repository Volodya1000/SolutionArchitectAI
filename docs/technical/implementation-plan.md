# План реализации MVP

[Навигация](README.md) · [BRD](../BRD.md) · [Согласование](../review.md)

Текущая работа — два документарных PR: корректировка #4 и stacked актуализация BRD/примера/LaTeX/PDF. Merge выполняет человек. Следующие пункты — содержательные результаты разработки, а не обязательное число PR; соседние шаги можно объединять при читаемом diff. Нет отдельных пустых PR ради инфраструктуры и нет реализации backend/frontend в документарных PR.

## 1. Первый работающий чат React → FastAPI → LLM

Вместе с минимальным каркасом получить сохраняемый диалог: React/Vite, assistant-ui adapter, FastAPI/Dishka, PostgreSQL/SQLAlchemy/Alembic, LiteLLM к настроенному endpoint LM Studio. Несекретный YAML/Settings, lock-файлы, Compose приложения и PostgreSQL, Ruff/Pyright/pytest/import-linter и frontend checks входят в этот же результат. Не откладывать LLM до завершения всех каталогов архитектуры.

Готовность: создать два чата, отправить/stream/отменить ответ, восстановить историю после restart, увидеть error/incomplete, переключить Light/Dark/System с сохранением. Fake endpoint в обычном CI и отдельный реальный локальный smoke с зафиксированной моделью/capabilities. Приложение пока не объявляет архитектуру согласованной. Пустые пакеты и макет не считаются первым рабочим сценарием.

## 2. Общая модель, дерево и безопасная работа задачи

Устойчивые ID, JSON schema_version/детерминированная сериализация, независимые валидаторы, общий Git repo на пространство и task branch от точного main. UI дерева/свойств/where-used, локальный файловый порт и immutable upload/source pin, PostgreSQL journal и idempotency. S3 adapter добавляется к тому же контракту при проверке storage portability, MinIO опционален.

Готовность: один общий компонент на двух видах, изменение имени видно в обоих, layouts сохранены; удаление из вида не удаляет каталог; неизвестная ссылка/версия/duplicate key отклоняются без потери модели. Принятая человеком правка коммитится только в task branch; crash до/после ref update и повтор operation_id не создают дублей. ИИ не выполняет merge. Реальный Git/PostgreSQL/local integration и S3 contract suite проверяют соответствующие адаптеры.

## 3. Анализ BRD, вопросы и типизированное предложение

Общий StructuredOutputGenerator (Instructor + LiteLLM + Pydantic), RetryConfig, промпты по Python-файлам, ContextBuilder, persisted pipeline. BRDAnalysisAgent и ClarificationAgent; ответы — use case, не домысел агента. ArchitectureDesignAgent использует те же механизмы, специализация данных/интеграций — схемы/промпты, не отдельные сервисы.

Готовность: source refs, закрытые вопросы не дублируются, ожидание ответа переживает restart, отмена/deadline/capability error видны. Counts сетевых и validation retries ограничены общим бюджетом. Смена LM Studio → vLLM/другой поддерживаемый endpoint меняет конфигурацию, не агента. Stale proposal не применяется; обязательные правила не выпадают при переполнении контекста. Допущение связано с A-01/A-07 и не отменяет стандарт.

## 4. Представления, независимый judge и разрешённая интеграция

Расширить вертикальный сценарий до A-01–A-07, .puml/SVG, формальных graph/rule checks и ArchitectureReviewAgent. Принятие, согласование и merge различимы; обычный human Git workflow и регистрация результата merge без обязательного GitLab MR.

Готовность: направления данных/вызовов/ответов и Access read/write сохранены на reporting-system; исключённый актив каталога не ложный isolated defect. Judge не отменяет формальную блокировку. Человек видит сомнительные AI proposals и доказательства до решения. После main update — ручное разрешение конфликтов и новые checks/approval; согласованный tree сопоставлен фактическому merge. История/revert создают новые изменения, sources удерживаются, зависимые проверки инвалидируются. Diagram palettes читаемы в обеих темах, export не зависит от LLM.

## 5. Приёмка синтетического MVP

Размеченный набор и проверки готовятся в предыдущих шагах, не откладываются целиком сюда. Согласовать редакцию требований/эталона и запустить воспроизводимые eval на выбранных локальных моделях: Faithfulness, Citation Faithfulness, полнота генерации, корректность объектов/связей, полнота нарушений, ложные замечания и необоснованные предложения. Нет заранее согласованных числовых порогов смыслового качества.

Готовность: формальные контрольные дефекты детерминированно обнаруживаются; корректные случаи не блокируются; фактические LLM-метрики отделены от fake-тестов. Сквозной Playwright проходит чат → вопросы → предложение → проверки → принятие → история с настоящими DB/Git. Restore backup проверяет источники и операции. XML-экспорт включается только после отдельного решения о необходимости Archi. Реальные данные и удалённый доступ остаются за отдельными согласованными требованиями.

После этого — разработка по обнаруженным ограничениям, а не новая серия абстракций. Semantic RAG, LangGraph, Tool Calling, горизонтальные workers и federation repo вводятся только для конкретного измеренного сценария.
