# План реализации MVP

[Навигация](README.md) · [BRD](../BRD.md) · [Оркестрация](agent-pipeline.md)

Текущий пересмотр — документация и оформление трёх PDF; backend/frontend и реальные LLM в этом PR не реализуются. Шаги ниже задают очередность работающих результатов, не обязательное число будущих PR. Версии библиотек фиксируются совместно в lock-файлах при реализации.

## 1. Первый работающий чат React → FastAPI → LangChain → локальная LLM

С минимальным каркасом получить сохраняемый диалог без внешнего LLM API-ключа: Python 3.13/uv, React/Vite/shadcn/ui/Tailwind CSS, выбранный assistant-ui adapter, FastAPI/Dishka, PostgreSQL/SQLAlchemy/Alembic, `langchain-core` и `langchain-openai` к vLLM из `docker-compose.ln.yml` с поддерживаемой локальной моделью. LangGraph этому сценарию не нужен. Несекретный YAML/Settings, `docker-compose.yml` и `docker-compose.ln.yml`, Ruff/Mypy/Pylint/Bandit/import-linter/WPS231/pytest и frontend checks входят в тот же результат. LLM не откладывается до завершения архитектурных каталогов.

Готовность: два чата, отправка/stream/отмена ответа, история после restart, видимый error/incomplete и Light/Dark/System. Обычный CI использует fake endpoint, отдельный smoke — реально выбранную модель. Для менее мощного компьютера предусматривается компактный проверенный профиль или демонстрационный fake LLM; fake не показывает качество агентного проектирования. Приложение пока не объявляет архитектуру согласованной.

## 2. Общая модель и безопасная предметная операция

Python Domain Model с разрешёнными операциями и инвариантами, общий Git repo на пространство, task branch от точного `main`, JSON сериализация, React Flow для интерактивных видов, UI дерева/свойств/where-used, immutable файлы и PostgreSQL journal/idempotency. S3 adapter добавляется по тому же файловому контракту при проверке переносимости.

Готовность: один объект на двух видах, независимые layouts, отклонение нарушений инвариантов, запись только в task branch после решения человека; crash и повтор `operation_id` не создают второй commit. Реальные Git/PostgreSQL/local integration проверки обязательны.

## 3. Первый сквозной граф: извлечение → вопрос → ответ → возобновление

Ввести `StructuredOutputGenerator` на LangChain/Pydantic, `RetryConfig`, раздельные Python-промпты, ContextBuilder, RequirementsExtractionAgent и ClarificationAgent. `StateGraph` и `AsyncPostgresSaver` сохраняют процесс, `interrupt()` ждёт ответа архитектора, `AnswerClarification` проверяет права/ревизию, затем граф возобновляется. GraphState хранит ссылки и версии, Application — предметные операции. Никакой второй машины стадий.

Готовность: вопросы и source refs не теряются после restart; закрытые вопросы не дублируются; новая входная ревизия помечает результат stale; повтор узла безопасен. Профили выбранных локальных моделей и vLLM проверяются отдельно. Интеграционные испытания с реально выбранными моделями/серверами должны проверить native JSON Schema, невалидный JSON/Pydantic, корректирующую генерацию, отказ от скрытого Tool Calling, общий бюджет retry/deadline, timeout/rate limit/cancel и освобождение async-ресурсов. Эти испытания ещё не выполнены.

## 4. Проектирование, представления и независимое ревью

Расширить LangGraph отдельными операциями контекста, reuse, компонентов, данных, потоков, взаимодействий, сборки кандидата и ArchitectureReviewAgent согласно [зависимостям](agent-pipeline.md); не начинать с полного графа. Application/Domain определяют затронутые результаты и проверяют версии входов. Граф выполняет выбранные операции и независимые ветви. Формальные проверки, локальный PlantUML Server в отдельном Compose-сервисе, .puml/SVG и решение человека остаются отдельными шагами; принятие, согласование и merge различимы.

Готовность: конкурентные независимые операции не делят SQL session, конфликты общих ID разрешаются явно; смена Git revision запускает проверку актуальности; replay узла не повторяет предметную команду/commit. Проверить прерывание и возобновление после перезапуска, повторный запуск узла и корректный shutdown checkpointer. Judge не отменяет формальную блокировку.

## 5. Приёмка синтетического MVP

Согласовать редакцию требований/эталона и провести воспроизводимые оценки на выбранных локальных моделях: Faithfulness, Citation Faithfulness, полнота генерации, корректность объектов/связей, полнота нарушений, ложные замечания и необоснованные предложения. Числовые цели смыслового качества пока не утверждены.

Готовность: сквозной Playwright проходит чат → вопрос → предложение → проверки → принятие → историю с настоящими DB/Git; backup/restore проверяет источники и незавершённые операции. Реальные данные и удалённый доступ требуют отдельных требований. Semantic RAG, Tool Calling и горизонтальные workers вводятся при подтверждённой необходимости.
