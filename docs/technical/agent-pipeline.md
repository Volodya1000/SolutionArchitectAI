# Оркестрация и операции проектирования

[Навигация](README.md) · [Роли агентов](agents.md) · [Lifecycle](resource-lifecycle.md)

**Решение для многоэтапного проектирования — LangGraph `StateGraph` с явными, преимущественно детерминированными переходами.** Он выполняет зависимости, ветвление и независимые операции, сохраняет checkpoints и обеспечивает прерывание/возобновление. Не строим собственную универсальную машину стадий с теми же переходами и checkpoint: следующий узел и состояние выполнения принадлежат LangGraph. [Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api), [interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) и [PostgreSQL checkpointer](https://github.com/langchain-ai/langgraph/tree/main/libs/checkpoint-postgres) покрывают эту сложность. Опыт организации с LangChain/LangGraph упрощает передачу проекта, но это решение ещё требует испытаний в приложении.

Первому чату React → FastAPI → LangChain → локальная LLM LangGraph не нужен. Первый графовый сценарий: извлечение требований → обнаружение блокирующего вопроса → `interrupt()` → ответ архитектора через Application → `Command(resume=...)` с тем же `thread_id`. Затем граф расширяется отдельными операциями проектирования и review. Нет автономного выбора переходов LLM, динамического tool loop или Tool Calling ради LangGraph. Применение предложения, архитектурное согласование и Git merge — отдельные предметные команды человека, вне полномочий графа.

## Граница графа и приложения

Frontend/FastAPI принимают действия и показывают процесс. Application создаёт run, проверяет доступ и ревизии, связывает результат с задачей, Git и согласованием. LangGraph ведёт только исполнение графа. Узел вызывает агент через `AgentRequest → AgentResult` и переводит результат в обновление GraphState; агент не обязан знать тип состояния графа. LangChain обслуживает LLM, Domain проверяет допустимые операции и инварианты, Persistence/Infrastructure реализуют PostgreSQL, Git, файлы и LLM-адаптеры. Граф не является источником истины архитектуры и не записывает подтверждённую модель в обход Application/Domain.

В PostgreSQL `langgraph-checkpoint-postgres` хранит checkpoints выполнения. Для async backend выбран кандидат `AsyncPostgresSaver`; соединение/checkpointer живёт в управляемом `async with` на lifespan worker, а не создаётся на каждый HTTP-запрос. `.setup()` явно запускается при инициализации/миграции, до первого использования. При ручном соединении нужны `autocommit=True` и `row_factory=dict_row`. Сериализация ограничивается безопасными типами; [официальный README](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/README.md#security) рекомендует `LANGGRAPH_STRICT_MSGPACK=true` или список разрешённых модулей. `pickle_fallback` не включаем. Версии и способ подключения проверяются с реальной PostgreSQL перед реализацией.

GraphState компактен: run_id, ссылки и версии входных документов, base Git revision, ссылки на результаты, необходимые управляющие данные и данные для resume. Полная корпоративная архитектура и SQL-журнал предметных операций в каждом checkpoint не сохраняются. Подробности загружаются из авторитетных хранилищ. Application отдельно хранит права, task/run IDs, ответы/согласования, Git-связи и `operation_id` применённых изменений. Нет второго хранилища переходов с собственным next-stage и дублирующими checkpoints.

## Единицы процесса

Агент — компонент с ролью; LLM-вызов — отдельная генерация; узел графа — исполняемая операция или барьер процесса; use case — операция Application (StartDesign, AnswerClarification, ResumeRun, ApplyProposal). Один агент выполняет несколько вызовов; один узел может вызвать соответствующую роль агента или детерминированную проверку. Use case управляет правами/состоянием, а не служит синонимом агента.

Минимальная композиция сохраняет RequirementsExtractionAgent, ClarificationAgent, ArchitectureDesignAgent и независимый ArchitectureReviewAgent. Внутри проектирования — следующие сохраняемые операции, а не один огромный запрос. Один шаг может делиться на пакеты по источникам/затронутым ID; каждый вызов имеет отдельные attempt_id, prompt и схему результата. Явные переходы и зависимости задаёт StateGraph, LLM не планирует собственные полномочия.

| Операция / цель | Вход → структурированный результат | Зависимости / параллелизм | Проверка и условие повтора / влияние |
| --- | --- | --- | --- |
| E. Извлечь FR/NFR | Версии документов/фрагменты/coverage → RequirementsExtraction с source refs, gaps, conflicts и отдельными assumptions | Независимые документы параллельно, затем сведение; противоречия не устраняются молча | Проверка локаторов и покрытия; новая версия повторяет затронутые пакеты и их сведение, инвалидирует зависимые шаги |
| Q. Уточнить | E, gaps, ответы и закрытые gap_key → ClarificationSet/NeedsInput | Независимые вопросы группируются; зависимое проектирование ждёт ответа, остальное продолжается | Сверка дубликатов/полномочий; новое основание явно reopen; ответ инвалидирует только зависящие от него операции |
| C. Проанализировать контекст | Принятые требования, существующая архитектура, правила/решения → ContextAnalysis: границы, ограничения, затронутые ID, зависимости и нерешённые вопросы | После E/Q для данного среза; непересекающиеся срезы параллельно | Проверка coverage и актуальной ревизии; изменения источников/каталога/границ повторяют C и зависимые планы |
| R. Найти повторное использование | C, каталог, интерфейсы → ReusePlan: кандидаты существующих ID, пригодность, пробелы, основания отказа | После C; поиск по независимым областям параллельно, сведение до новых компонентов | Сверка идентичности и ограничений; изменение кандидата повторяет затронутый поиск, затем N/D/I |
| N. Предложить компоненты | C/R, требования и решения → ComponentPlan с новыми локальными ключами, ответственностями и альтернативами | После R; независимые подсистемы параллельно, конфликт общей ответственности разрешается до продолжения | Дубли/необоснованные компоненты/покрытие; замечание повторяет затронутую часть и её D/F/I/V |
| D. Спроектировать данные | C/R/N, требования к данным → DataPlan: наборы, владельцы, хранилища, преобразования, классификация | После R/N; с черновым I параллельно только при стабильных общих контрактах | Доменные/архитектурные правила, ссылки/основания; изменение данных повторяет связанные F/I/V |
| F. Спроектировать потоки | D и компоненты, обязательные сценарии → FlowPlan: источник, проверка, запись/чтение, преобразование, объединение, получатель | После D; независимые сценарии параллельно | Направления/достижимость/граничные роли; изменение потока повторяет связанные I/V и checks |
| I. Спроектировать интерфейсы/интеграции | N, F, существующие интерфейсы и безопасность → IntegrationPlan: инициатор, получатель, интерфейс, протокол/защита, связь с потоком | Финал после F; предварительный независимый анализ протоколов допускается после N | Проверка совместимости и source refs; изменение endpoint/инициатора повторяет связанные F при изменении семантики, V/checks |
| A. Собрать кандидата и ограничения | Согласованные планы R–I, base snapshot → ChangeProposal и кандидат Domain | Последовательный детерминированный барьер; без LLM | Структурные инварианты и ссылки проверяются до коммита; топология и обязательные правила — асинхронно после него, с записью открытых нарушений в A-07 без блокировки рабочей ветки |
| V. Обновить представления | Проверенный кандидат, профили, старый layout → ViewPlan при необходимости LLM и детерминированные проекции | Независимые виды параллельно; после A | Соответствие каталогу, профилю и потокам; правка layout повторяет только вид, семантическая правка идёт через A |
| J. Независимое ревью | Immutable кандидат/diff, источники, FormalReport и виды → ReviewReport | После завершения обязательных формальных проверок данной редакции; независимые области review параллельно с общим сведением | Основания/покрытие, Faithfulness/Citation Faithfulness; замечания идут в Q/C/R/N/D/F/I/V по ID, затем повторяются затронутые checks и review |
| H. Решение человека | Diff, влияние, оба отчёта → accept/reject/request_changes и отдельно approval | После J; ApplyProposal — отдельный use case, не LLM | Expected head и актуальные входы; отказ/правка повторяют затронутые шаги; commit/approval/merge различны |

Формальные проверки выполняются и после частичных предложений: некорректный план не передаётся дальше как корректный. Частичный результат можно сохранить как draft с диагностикой. Модель изменяется разрешёнными предметными операциями после решения человека; планы LLM сами её не мутируют.

## Частичный пересчёт и возобновление

Application/Domain определяют, какие результаты стали неактуальны: для операции сохраняются версии/digests входов, read/write ID sets и output ref. Изменение требования, источника или общей модели помечает зависящие результаты stale; транзитивно повторяются **затронутые** операции с проверкой версий на входе и перед применением. При неопределённом влиянии пересчитывается затронутый срез. LangGraph исполняет выбранные узлы, но не вычисляет семантическую инвалидацию автоматически. Универсальный механизм для всех возможных графов сейчас не нужен.

Независимые операции читают immutable snapshot и имеют отдельные execution scopes/SQL sessions. Параллельные результаты сводятся с проверкой конфликтов общих ID и предусловий; порядок завершения не решает предметный конфликт. D → F → I сохраняет зависимости и барьеры. Ограничение конкуренции и общий deadline обязательны.

При `interrupt()` состояние сохраняется; при `Command(resume=...)` узел начинается заново, включая код перед прерыванием. Поэтому неидемпотентные внешние действия перед ним запрещены без защиты. В ожидании нет открытой coroutine/SQL-транзакции. Для применения Git используется отдельный Application use case с `operation_id`, expected head, журналом и восстановлением, а не replay всего узла. Если входная ревизия изменилась, поздний результат остаётся черновиком. Отмена и восстановление согласуются с журналом; при ответе/согласовании полномочия проверяются вновь. LangGraph не предоставляет общую транзакцию PostgreSQL/Git/S3.

Повторный запуск узла может повторить LLM-вызов. `StructuredOutputGenerator` владеет единым бюджетом попыток и времени внутри генерации; retry policy LangGraph для такого узла не создаёт независимый второй цикл. На границах восстановленного запуска Application проверяет сохранённый остаток бюджета/политику, чтобы повторы не умножались незаметно. Для ошибок внешних операций действуют отдельные идемпотентные команды и явные правила восстановления.

Выделение DataDesignAgent/IntegrationDesignAgent возможно позже при реально разных контрактах или ответственности. Пока достаточно схем и промптов операций внутри ArchitectureDesignAgent. Один вызов на всю архитектуру затрудняет локальные проверки; агент на каждую строку таблицы не добавляет новой границы.
