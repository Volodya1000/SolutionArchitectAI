# Оркестрация и стадии

[Навигация](README.md) · [Роли агентов](agents.md)


RequirementsExtraction → Clarification → ожидание/ответ человека → ArchitectureDesign → формальные валидаторы → ArchitectureReview → решение человека → применение. Независимый анализ разрешён при открытых вопросах; зависимые стадии ждут. Применение и согласование различаются, [merge](git-workflow.md) выполняется отдельно человеком.

| Критерий | A: детерминированный application pipeline | B: LangGraph |
| --- | --- | --- |
| Код и читаемость | Небольшая явная таблица стадий/переходов; сами пишем claims, resume и журнал | Nodes/state/edges и готовые interrupts/checkpoints; дополнительный runtime и mapping |
| Тестируемость | Каждый переход/use case с fake-портами; контракт PostgreSQL/Git проверяется отдельно | Удобные тесты узлов/переходов; replay/interrupt тоже требуют сценариев |
| Состояние/HITL | PostgreSQL RunState, waiting_input без живой coroutine, resume use case | Checkpointer и thread_id, interrupt/resume из framework |
| Сбой/отмена | Interrupted + повторное выполнение безопасной стадии; собственный ограниченный recovery | Готовые checkpoints уменьшают код восстановления, side effects всё равно должны быть идемпотентны |
| PostgreSQL/Git | Один журнал команд приложения; SQL транзакция только SQL | PostgreSQL checkpointer возможен; не объединяет Git/S3 с SQL и может дублировать RunState |
| Когда окупается | Линейный MVP с несколькими развилками | Большое ветвление, циклы, подграфы и сложные повторные исполнения |

**Рекомендация — A.** Это реальная персистентная машина переходов, не цепочка вызовов в HTTP router. Сохраняются run_id, typed stage/status, stage input/output refs, state_version, branch/base_commit, prompt/model config digest, счётчики повторов, lease и ожидаемые question IDs. Переход — короткая SQL CAS-команда. waiting_input переживает restart; после ответа новый execution scope продолжает run с проверкой ревизии. Неоконченная running стадия становится interrupted, автоматическое повторное применение запрещено. Лимиты повторов стадии и LLM retries различаются. [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence) не отвергается вообще, но сейчас дублирует значительную часть обязательного журнала предметных команд.

Tool Calling в MVP отсутствует: нет динамического реестра tools, model-driven цикла, shell или самостоятельной записи ИИ. Structured output использует JSON Schema/JSON text, а не скрыто выбранный tool mode.

## Единицы процесса

Агент — компонент с ролью; LLM-вызов — отдельная генерация; pipeline stage — сохраняемый шаг/барьер процесса; use case — операция Application (StartDesign, AnswerClarification, ResumeRun, ApplyProposal). Один агент выполняет несколько вызовов; одна стадия может вызвать extraction, clarification и review. Use case управляет правами/состоянием, а не служит синонимом агента.

Минимальная композиция сохраняет RequirementsExtractionAgent, ClarificationAgent, ArchitectureDesignAgent и независимый ArchitectureReviewAgent. Внутри проектирования — следующие сохраняемые операции, а не один огромный запрос. Один шаг может делиться на пакеты по источникам/затронутым ID; каждый вызов имеет отдельные attempt_id, prompt и схему результата. План зависимостей вычисляет оркестратор, LLM не планирует собственные полномочия.

| Операция / цель | Вход → структурированный результат | Зависимости / параллелизм | Проверка и условие повтора / влияние |
| --- | --- | --- | --- |
| E. Извлечь FR/NFR | Версии документов/фрагменты/coverage → RequirementsExtraction с source refs, gaps, conflicts и отдельными assumptions | Независимые документы параллельно, затем сведение; противоречия не устраняются молча | Проверка локаторов и покрытия; новая версия повторяет затронутые пакеты и их сведение, инвалидирует зависимые шаги |
| Q. Уточнить | E, gaps, ответы и закрытые gap_key → ClarificationSet/NeedsInput | Независимые вопросы группируются; зависимое проектирование ждёт ответа, остальное продолжается | Сверка дубликатов/полномочий; новое основание явно reopen; ответ инвалидирует только зависящие от него операции |
| C. Проанализировать контекст | Принятые требования, существующая архитектура, правила/решения → ContextAnalysis: границы, ограничения, затронутые ID, зависимости и нерешённые вопросы | После E/Q для данного среза; непересекающиеся срезы параллельно | Проверка coverage и актуальной ревизии; изменения источников/каталога/границ повторяют C и зависимые планы |
| R. Найти повторное использование | C, каталог, интерфейсы → ReusePlan: кандидаты существующих ID, пригодность, пробелы, основания отказа | После C; поиск по независимым областям параллельно, сведение до новых компонентов | Сверка идентичности и ограничений; изменение кандидата повторяет затронутый поиск, затем N/D/I |
| N. Предложить компоненты | C/R, требования и решения → ComponentPlan с новыми локальными ключами, ответственностями и альтернативами | После R; независимые подсистемы параллельно, конфликт общей ответственности разрешается до продолжения | Дубли/необоснованные компоненты/покрытие; замечание повторяет затронутую часть и её D/F/I/V |
| D. Спроектировать данные | C/R/N, требования к данным → DataPlan: наборы, владельцы, хранилища, преобразования, классификация | После R/N; с черновым I параллельно только при стабильных общих контрактах | Доменные/архитектурные правила, ссылки/основания; изменение данных повторяет связанные F/I/V |
| F. Спроектировать потоки | D и компоненты, обязательные сценарии → FlowPlan: источник, проверка, запись/чтение, преобразование, объединение, получатель | После D; независимые сценарии параллельно | Направления/достижимость/граничные роли; изменение потока повторяет связанные I/V и checks |
| I. Спроектировать интерфейсы/интеграции | N, F, существующие интерфейсы и безопасность → IntegrationPlan: инициатор, получатель, интерфейс, протокол/защита, связь с потоком | Финал после F; предварительный независимый анализ протоколов допускается после N | Проверка совместимости и source refs; изменение endpoint/инициатора повторяет связанные F при изменении семантики, V/checks |
| A. Собрать кандидата и ограничения | Согласованные планы R–I, base snapshot → ChangeProposal и кандидат Domain | Последовательный детерминированный барьер; без LLM | Инварианты, ссылки, обязательные правила; ошибка возвращается владельцу затронутого плана, не всей генерации |
| V. Обновить представления | Проверенный кандидат, профили, старый layout → ViewPlan при необходимости LLM и детерминированные проекции | Независимые виды параллельно; после A | Соответствие каталогу, профилю и потокам; правка layout повторяет только вид, семантическая правка идёт через A |
| J. Независимое ревью | Immutable кандидат/diff, источники, FormalReport и виды → ReviewReport | После обязательных формальных проверок; независимые области review параллельно с общим сведением | Основания/покрытие, Faithfulness/Citation Faithfulness; замечания идут в Q/C/R/N/D/F/I/V по ID, затем повторяются затронутые checks и review |
| H. Решение человека | Diff, влияние, оба отчёта → accept/reject/request_changes и отдельно approval | После J; ApplyProposal — отдельный use case, не LLM | Expected head и актуальные входы; отказ/правка повторяют затронутые шаги; commit/approval/merge различны |

Формальные проверки выполняются и после частичных предложений: некорректный план не передаётся дальше как корректный. Частичный результат можно сохранить как draft с диагностикой. Модель изменяется разрешёнными предметными операциями после решения человека; планы LLM сами её не мутируют.

## Частичный пересчёт и возобновление

Для каждой операции сохраняются input digest (ревизия модели, требования, выбранные и отвергнутые кандидаты, source/rule versions, решения), read/write ID sets, output ref, статус и зависимости. Отслеживается не только выбранный объект, но и область поиска: новый подходящий компонент инвалидирует R соответствующего каталога. Изменение общего объекта инвалидирует читающие его операции и транзитивных потребителей; layout конкретного вида не запускает извлечение требований. Если влияние определить достоверно нельзя, пересчитывается весь затронутый срез и это видно пользователю.

Параллельные задачи читают один immutable snapshot, не общую mutable модель и не одну SQL session. Оркестратор сводит результаты и выявляет конфликт записей по общим ID/предусловиям; конфликтующие предложения не объединяются по времени завершения. Ограничение concurrency, deadline, отмена и независимые execution scopes обязательны. Зависимые D → F → I выполняются последовательно; условная параллельность не снимает финального барьера согласованности.

Checkpoint — после каждой принятой операции/пакета, до ожидания человека и до внешнего side effect. Resume проверяет lease/state_version, fingerprints, актуальность head и незакрытые вопросы. Завершённые актуальные результаты используются снова; interrupted generation может выполниться повторно (ответ LLM не обещает побитовой идентичности), применение восстанавливается по operation_id без повторной публикации. Во время waiting_input нет живой coroutine или открытой транзакции. Изменение требований человеком во время run переводит зависимые результаты в stale; поздний ответ остаётся черновиком.

Выделение DataDesignAgent/IntegrationDesignAgent возможно позже при независимо меняющихся контрактах, командах/политиках моделей или отдельной ответственности. Сейчас схем/промптов операций внутри Design-роли достаточно. Альтернатива «один запрос на всю архитектуру» затрудняет локальные проверки/перезапуск; агент на каждую строку таблицы добавляет классы без новой границы. LangGraph рассматривается при измеренном усложнении ветвления и recovery, Tool Calling — только для конкретной необходимой операции с отдельной моделью прав.
