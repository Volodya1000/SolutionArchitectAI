## 2. Общие правила реализации

- **Вертикальные инкременты.** У каждого PR есть пользовательский или API-сценарий, собственные позитивные и негативные тесты и проверяемое состояние после merge. Никакого долгого «пустого» backend без интерфейса.
- **Последовательный merge.** Каждый следующий PR создаётся от актуальной `main` после принятия предыдущего. Эти девять PR — ориентировочные границы: при доказанной необходимости допустима корректировка размера, но не скрытое изменение требований. Одновременно не разрабатывать девять веток с конфликтующими контрактами.
- **Superpowers + Codex.** Для конкретного PR: изучить текущую кодовую базу и требования → brainstorming вариантов внутри принятой архитектуры → короткий design/spec → утвердить → `writing-plans` с файлами, интерфейсами, TDD-шагами и командами проверок → реализовать небольшими коммитами → независимое review → проверить → открыть PR. Не детализировать весь MVP одним огромным промптом.
- **Человек управляет архитектурой.** ИИ лишь предлагает. `ApplyProposal`, commit, approval и merge — разные операции. Агент не получает разрешение на изменение утверждённой модели, утверждение и merge.
- **Одна предметная модель.** Python Domain Model определяет объекты, отношения, операции и инварианты. JSON — сериализация в Git; документарная JSON Schema не становится источником бизнес-логики. Представления используют устойчивые ID одной модели, layout хранится на уровне вида.
- **Одна редакция для артефактов.** A-01–A-07, таблицы, SVG и `.puml` строятся из согласованных по структуре данных одной зафиксированной редакции. Отдельные агенты не генерируют семь независимых «истин». До финального approval материалы помечаются как черновые.
- **Два разных класса нарушений.** Синхронные структурные ошибки (невалидный JSON/Domain, отсутствующий объект, дубликат ID, обязательный атрибут) **не дают выполнить commit**, сохраняя черновик с диагностикой. Асинхронные нарушения топологии и архитектурных правил **не блокируют промежуточный commit**, но блокируют финальное согласование, если являются обязательными. Недостаток сведений не выдаётся за успешную проверку.
- **Идемпотентность с момента появления побочных эффектов.** В PR 3 операции и записи PostgreSQL защищены от повторного выполнения узла LangGraph. В PR 4 тот же принцип расширяется на Git и межхранилищное восстановление. Checkpoint LangGraph не означает «exactly once» для внешнего действия.
- **Воспроизводимость.** Закреплённые зависимости/lock-файлы, реальные PostgreSQL/Git/PlantUML integration-тесты по мере появления возможностей, fake LLM в обычном CI, отдельный smoke на реальном vLLM и выбранной модели.
- **Никакой фиктивной приёмки.** Частичное покрытие AC фиксируется как *partial*, а не *done*. Неиспытанные функции остаются «не проверено». Документация и успешный CI примера не заменяют runtime-проверки приложения.

### Локальная среда и границы первой поставки

- Windows Server 2022 + RTX 3060 12 GB, Docker Desktop с WSL2; путь репозитория в Windows или файловой системе WSL2 не фиксируется до отдельного решения о процессе разработки.
- `docker-compose.yml`: frontend, backend, PostgreSQL, локальный PlantUML Server, сохраняемые Git/file volumes; поддерживается fake LLM для воспроизводимого запуска.
- `docker-compose.vllm.yml`: подключаемый vLLM в той же Docker-сети с настраиваемым OpenAI-совместимым endpoint; *обязателен реальный smoke* на целевом GPU, но не в обычном CI.
- Точную локальную модель, квантование, контекст, допустимый offload и версии vLLM выбрать и закрепить после измерения. `openai/gpt-oss-20b` из технических решений — кандидат для подходящего оборудования, **не гарантированный профиль RTX 3060 12 GB**. Для этой машины нужен проверенный компактный профиль.
- Условие первого этапа: демонстрация обычного чата без внешнего LLM API-ключа. LangGraph, векторная БД, Redis, Kafka, эксплуатационная интеграция с банком и полноценная платформа IAM в PR 1 не нужны.
- Production/OpenShift, политики корпоративного доступа и реальные закрытые материалы требуют отдельной проверки; локальный MVP нельзя объявлять безопасным для production только на основании Compose.

## 4. Подробные границы и приёмка каждого PR

### PR 1. Приложение и первый рабочий чат

**Цель:** проверяемая цепочка `React → FastAPI → LangChain → PostgreSQL → LLM` на локальной машине; LangGraph ещё не требуется.

**В составе:**

1. Структура backend/frontend; Python 3.13, uv, FastAPI, Pydantic v2, Pydantic Settings, Dishka, SQLAlchemy 2.x и Alembic. Выбранные слои/пакеты не должны зависеть от внешних SDK в Domain.
2. React, TypeScript strict, Vite, React Router, TanStack Query, shadcn/ui, Tailwind CSS; `assistant-ui` с собственным FastAPI-адаптером; Light/Dark/System с сохранением выбора.
3. Минимальные сущности проекта/задачи для области чатов, чат, сообщение, run, persist status. Несколько отдельных чатов в одной области, история переживает перезапуск.
4. Контракт API для списка/создания чатов, сообщений, запуска и чтения статуса run, потока событий и server-side cancellation. Для стрима — упорядоченные события/последовательность, восстановление текущего состояния через API, различимые `queued/running/completed/failed/cancelling/cancelled/incomplete`. Разрыв SSE не равен отмене серверной генерации.
5. `langchain-core`/`langchain-openai`, настраиваемые `base_url`/model profile, потоковый обычный чат; test fake OpenAI-compatible endpoint, vLLM в отдельном Compose-файле.
6. `docker-compose.yml` и `docker-compose.vllm.yml`, volume для PostgreSQL/файлов/Git, локальный PlantUML Server для будущих этапов. `.env.example` без секретов, lock-файлы и воспроизводимые команды запуска.
7. Первые backend/frontend gates: Ruff (lint+format), Mypy strict, Pylint, Bandit, import-linter, точечный WPS231, pytest; TypeScript strict, ESLint, Prettier, Vitest, Playwright. Конфигурация должна проверять реальные файлы; не добавлять заглушки ради зелёного CI.

**Наблюдаемая приёмка:**

- [ ] Из чистого checkout поднимается основной Compose c fake endpoint; браузер подключается к API, открывается чат.
- [ ] Созданы два чата в одной области: ответ в одном не меняет историю другого; после restart оба доступны.
- [ ] Ответ появляется потоково; отмена отправляет server-side команду и фиксирует окончательный статус, а не только закрывает окно.
- [ ] Ошибка LLM, пустой/оборванный stream и недоступный PostgreSQL отображаются как ошибки/незавершённость без фиктивного полного ответа.
- [ ] Переключение чата при позднем событии не меняет другой диалог; повторный запрос при reconnect не запускает вторую генерацию.
- [ ] Три темы работают и выбор переживает перезагрузку; keyboard navigation и базовая читаемость проверены в чате.
- [ ] Отдельный документированный smoke с **настоящей локальной моделью на RTX 3060 12 GB** успешно завершает запрос и поток ответа без внешнего API-ключа; указаны model ID, версии сервера, GPU-параметры и фактическое потребление ресурсов.
- [ ] Позитивный и негативный E2E/HTTP тест, unit/integration tests и все настроенные проверки проходят.

**Явно не входит:** документы и их версии, LangGraph, архитектурная Domain Model, React Flow, оценка качества проектирования. Поэтому **AC-18 и AC-19 закрыты лишь частично**: части про файлы, длительный агентный процесс и диаграммы появятся позже.

### PR 2. Версионирование документов и извлечение требований

**Цель:** входной материал становится воспроизводимым источником требований, а не просто вложением к сообщению.

**В составе:**

1. `FileStorage` на локальной файловой системе, PostgreSQL metadata с `file_id/version_id/SHA-256/MIME/size/storage_key/scope`, immutable содержимое и ссылки на сообщения/документы. Повторная загрузка новой редакции не перезаписывает старую.
2. Текст/Markdown как гарантированный первый вход. PDF вводится при проверенном извлечении текста и локаторов страниц; поддержку DOCX оценить по требованиям/тестам, не обещать корректный парсинг всех форматов без проверки.
3. `SourceRef` с конкретным документом, версией, локатором (раздел/страница/фрагмент) и подтверждающим текстом. Проверка фактического существования, хэша и доступа к источнику.
4. `StructuredOutputGenerator` (LangChain/Pydantic): явные профили native JSON Schema либо строго валидируемого JSON fallback, общий `RetryConfig`/deadline/cancel, типизированные ошибки. Никакого скрытого Tool Calling или автоматического ослабления схемы.
5. `RequirementsExtractionAgent`, `ContextBuilder`, доверенные системные инструкции отдельно от содержимого документов. Извлечение FR/NFR, целей, границ, ролей, данных, ограничений, пробелов и конфликтов — как кандидатов с происхождением. Начальный A-01.
6. UI: загрузка, версия/размер/тип, список извлечённых требований, открытие подтверждающего места, видимый статус ожидания проверки.

**Наблюдаемая приёмка:**

- [ ] После загрузки синтетического BRD получены типизированные требования со ссылками на реальные версии и фрагменты; отсутствие основания отображается явно.
- [ ] Старая версия остаётся читаемой после загрузки новой; неверный hash/повреждение/недостаточные права вызывают диагностируемый отказ, а не подстановку нового файла.
- [ ] Невалидный JSON/Pydantic output, исчерпанный retry budget и cancel дают typed failure без фиктивного результата.
- [ ] Документ с prompt injection не получает system-полномочия; текст источника не становится командой.
- [ ] Есть positive/negative integration tests на реальном локальном хранилище и выбранной паре LLM/vLLM; CI использует fake endpoint.

**Уточнение границ PR 2 (26.11.2026):** по согласованному заданию минимальный `StateGraph` и `AsyncPostgresSaver` введены уже здесь: подготовка → извлечение частей → объединение → проверка → сохранение через Application. SQL-идемпотентность и общий сохраняемый бюджет защищают повтор узлов. `interrupt()`, вопросы, ответы и Human-in-the-loop остаются PR 3.

**Дальше:** Diff требований и снятие согласований пока не «готовы». В этом PR создаётся основа неизменяемых версий и источников. AC-02/AC-18 — partial.

### PR 3. LangGraph, вопросы и Human-in-the-loop

**Цель:** извлечение → блокирующий вопрос → ответ человека → возобновление без потери и дублирования результата.

**В составе:**

1. `ClarificationAgent` и типизированный `ClarificationSet`: `question_id`, устойчивый `gap_key`, blocking, основание, зависимые требования. Закрытый вопрос не повторяется без изменившегося основания.
2. `StateGraph` с явными детерминированными переходами, `AsyncPostgresSaver` с управляемым жизненным циклом, безопасной сериализацией, `interrupt()` и `Command(resume=...)` с прежним `thread_id`.
3. `AnswerClarification` и `ResumeRun`: проверка идентификатора вопроса, ревизии, полномочий, версии источников; вопрос блокирует только зависимое проектирование.
4. **Минимальная PostgreSQL-идемпотентность:** уникальный `operation_id` + digest payload/scope, журнал результата и атомарная запись ответа/изменения статуса. Replay узла или повтор HTTP после timeout не дублирует вопрос, ответ, риск либо иные внешние SQL-записи.
5. Компактный GraphState хранит идентификаторы и версии входов/результатов, но не копию полной архитектурной модели. Нет второй собственной state machine для следующего этапа.
6. UI-карточки вопросов, ответов, подтверждённых допущений и связанных рисков A-01/A-07; состояния waiting_input, resume, cancelled, failed.

**Наблюдаемая приёмка:**

- [ ] На **отдельном неполном синтетическом сценарии** агент обнаруживает блокирующий пробел и останавливает зависимый узел. Полный эталон `reporting-system` не портить выдуманными пробелами: в нём вводных достаточно.
- [ ] После restart backend + PostgreSQL возобновление с исходным `thread_id` учитывает введённый ответ; связанные результаты и source refs воспроизводятся.
- [ ] Повтор `AnswerClarification`, повторное выполнение узла и crash между побочным SQL-действием и checkpoint не создают дубликатов; повтор с тем же ключом, но другим payload отклоняется.
- [ ] Принятое допущение отображается как «Подлежит верификации» в A-01 и имеет связанный риск A-07; не становится подтверждённым фактом.
- [ ] Отмена, timeout и закрытие ресурсов не оставляют «успешный» завершённый результат или утёкшие SQL sessions.

**Граница:** это защита от повторных **предметных побочных эффектов**, не гарантия единственного физического LLM-вызова при сетевых сбоях. Git-идемпотентность будет добавлена в PR 4. AC-01/AC-10 реализуются на предусмотренных сценариях, AC-18 остаётся partial.

### PR 4. Python Domain Model, Git и безопасные предметные операции

**Цель:** зафиксированная общая модель архитектуры с реальными Git-редакциями и едиными инвариантами для API/агентов.

**В составе:**

1. Python Domain: системы/компоненты, данные, интерфейсы, отношения, решения, источники, происхождение, статусы контроля, дерево views, ссылки на общие IDs; предметные команды вместо произвольного JSON Patch.
2. Детерминированный JSON round-trip, версия формата и явный mapping. Синхронные проверки перед commit: уникальность ID, валидность ссылок/обязательных полей, синтаксис/структура входа. Некорректное изменение остаётся черновиком.
3. Один общий архитектурный Git repo на пространство, `main` согласованной модели, `task/<id>` от точного SHA `main`, compare-and-swap `expected_head`, чтение immutable revisions, diff и базовые операции с моделью через API.
4. Продолжение журнала PostgreSQL: `operation_id`, expected head, payload digest, стадии prepared/published/completed, recovery после сбоев Git/SQL, защита от повторного commit. Реальные локальные Git integration tests.
5. Основа `Approval`/`Decision`/`ValidationResult` как данных и статусов без реализации финального утверждения и merge. Разделены provenance, quality/status и approval. Коммит не означает согласования.
6. Область/права и история изменения общих объектов. ИИ по-прежнему пишет `ChangeProposal` в PostgreSQL, но не делает Git commit самостоятельно.

**Наблюдаемая приёмка:**

- [ ] Созданы две task branches от известного `main`, а сам `main` не меняется от применения черновой операции.
- [ ] Domain round-trip сохраняет устойчивые IDs; чтение старой редакции воспроизводимо.
- [ ] Дубликат ID, отсутствующий endpoint связи, пропущенное обязательное поле или повреждённый JSON **блокируют commit**; исходная редакция сохраняется, черновик содержит локализованную ошибку.
- [ ] Семантически запрещённая правилами, но **структурно корректная** связь может сохраниться в промежуточном commit; соответствующая проверка получает состояние open/unverified до внедрения конкретных правил в PR 6–8. Она **не считается прошедшей**.
- [ ] Повтор operation_id после сбоя/рестарта не создаёт второй commit; конфликт ожидаемого HEAD не приводит к потере уже записанной модели.
- [ ] Предметные команды проверяются через API и реальный Git/PostgreSQL; полноценный React Flow **не нужен до PR 5**.

**Граница:** модель статусов создаётся сейчас, финальная проверка возможности approval, согласование точного Git tree и merge — в PR 9. AC-06/11/17 partial.

### PR 5. Интерактивные представления, свойства, diff модели

**Цель:** архитектор редактирует общую модель через интерфейс, а не вручную правит JSON.

**В составе:**

### PR 6. ИИ проектирует данные, потоки и DFD

**Цель:** получить архитектуру данных по требованиям и корпоративному контексту, сохранив возможность человеческой правки.

**В составе:**

1. Операции `ArchitectureDesignAgent`: анализ контекста/существующих активов, выбор источников и наборов данных, классификация, хранение, периодичность, назначение, построение потоков, обоснования и существенные альтернативы.
2. Типизированные `ChangeProposal` с командами Domain, ссылками на требования, стандарты и редакции; отсутствие контекста обозначается неопределённостью, а не догадкой.
3. A-02 (каталог данных/матрица потоков) и A-03 (DFD/ArchiMate по принятому профилю) из **одной модели и её версии**; локальный PlantUML Server, `.puml` и SVG, воспроизводимая регенерация без LLM.
4. **Первые топологические валидаторы потоков:** направления, чтение/запись, входы/выходы с допустимыми terminal/source/storage roles, «чёрная дыра», «чудо», изоляция в проверяемой области, достижимость обязательного получателя в доступном профиле.
5. Синхронные структурные ошибки остаются blocking до commit, доказанные архитектурные нарушения записываются асинхронно после commit. Неполная область проверки — `not checked`, не `passed`.

**Наблюдаемая приёмка:**

- [ ] Из синтетических требований и каталога создаётся кандидат данных/потоков с проверяемыми основаниями и вариантами; источник данных и инициатор технического вызова не смешиваются.
- [ ] Архитектор может изменить/отклонить поток без повторного переписывания подтверждённых решений агентом.
- [ ] `.puml`/SVG и таблицы соответствуют одному snapshot; повторный render без LLM сохраняет смысл.
- [ ] Намеренно внесённые «чёрная дыра»/«чудо»/недостижимый поток выявляются, законные источники и конечные получатели не дают ложной блокировки.
- [ ] Асинхронное нарушение видимо и не мешает промежуточному commit; структурная ошибка не проходит.

**Граница:** не заявлять полноту AC-03/12 без всех интеграционных связей и независимых проверок PR 7–8. Полный пример содержит готовые требования и контекст; отдельные неполные кейсы тестируются независимо.

### PR 7. ИИ проектирует интеграции и межсистемные взаимодействия

**Цель:** построить техническую картину на основе утверждённых требований/данных, не выдумывая внешние зависимости.

**В составе:**

1. Операции `ArchitectureDesignAgent` для выбора/переиспользования систем, сервисов, interfaces, initiators/receivers, protocols, exchange modes, protection и связи с потоками A-02/A-03.
2. A-04 (каталог систем/матрица интеграций) и A-05 (ArchiMate виды взаимодействий) из общей модели; PlantUML `.puml`/SVG с общей редакцией A-06.
3. Первые **детерминированные проверки интеграционных ограничений**: допустимые типы/концы связей, инициатор вызова vs направление данных, наличие защищённого канала/разрешённого получателя, соблюдение синтетических SEC/ARCH/VIEW-правил, применимость исключений.
4. Использование уже заданного корпоративного контекста: Kafka, PostgreSQL, технологический/бизнес-прокси, системы доступа и передачи отчётов; объяснение, почему актив выбран либо отклонён, а не произвольное использование всего каталога.
5. Сохранение связи data flow ↔ technical interaction и предупреждение об изменении связанных потоков/видов.

**Наблюдаемая приёмка:**

- [ ] Для системы отчётности появляются понятные A-04/A-05 с основаниями и общей моделью.
- [ ] Запрещённый прямой выход, неверный канал для конфиденциальных данных, неверная направленность вызова и запрещённая связь выявляются с ID правил.
- [ ] Отсутствие корпоративного контекста даёт вопросы/допущения, не вымышленный протокол или внешнюю систему.
- [ ] Верная граница роли или разрешённое формально исключение не вызывают ложного блокирования.
- [ ] Нарушение обязательного правила не блокирует промежуточный commit и сохраняется для будущего approval gate.

**Граница:** уже реализованные валидаторы PR 6 используются повторно; PR 8 объединяет их в полноценный отчёт и дополняет независимым LLM review.

### PR 8. Комплексная формальная проверка и отдельный LLM-ревьюер

**Цель:** воспроизводимая диагностика одной зафиксированной версии с разделением факта нарушения и гипотезы ИИ.

**В составе:**

1. Единый запуск formal verification на version-pinned Domain/BRD/context/rules; sync structure vs async topology/business/notation. Статусы конкретной проверки: passed, violation, not applicable, not checked; журнал успешных и неуспешных проверок.
2. `ArchitectureReviewAgent` получает неизменяемые candidate/diff, formal report, requirements, standards; отдаёт структурированный `ReviewReport` со scope, source refs, вероятными проблемами и объяснениями, без прав commit/approval.
3. A-07: архитектурные решения и альтернативы, риски допущений, нарушения, неиспытанные обязательные условия, замечания judge, степень покрытия требований и версии правил. UI краткой сводки + подробного журнала/оснований.
4. Четыре итоговых статуса контроля объектов/связей по FR-09: «Нарушение» → «Недостаточно данных» → «Требует проверки» → «Подтверждено»; независимы от происхождения и состояния согласования.
5. Поддержка неформализованных требований: `not verified / manual verification`, ручное подтверждение покрытия конкретными объектами/связями. Обязательное непроверенное условие препятствует approval, а предположение judge само по себе не является доказанным дефектом.
6. Смена редакции корпоративного правила переоценивает затронутые элементы, показывает stale результаты и не переносит прежние подтверждения автоматически.

**Наблюдаемая приёмка:**

- [ ] Formal gate ловит заданные структурные и топологические дефекты; отчёт ссылается на конкретные объекты/правила/редакции.
- [ ] Judge обнаруживает и объясняет спорные проблемы как **предположения**, не скрывает formal violation и не меняет утверждённую модель.
- [ ] Проведены проверки корректных граничных случаев; не применимое и не проверенное не записываются как success.
- [ ] Новая редакция обязательного правила инвалидирует затронутые проверки/согласования, а исторический snapshot остаётся читаемым.
- [ ] Ручное подтверждение покрытия неформализованного требования явно связано с объектами/отношениями; без него обязательное условие остаётся открытым.

**Граница:** этот PR создаёт проверяемую основу approval gate, но само финальное Git-согласование и человеко-управляемый merge остаются в PR 9. Качество judge измеряется на синтетическом наборе, а не объявляется «доказанным» от наличия LLM.

### PR 9. Полное согласование, Git merge и приёмка MVP

**Цель:** пройти весь цикл «источники → требования → вопросы → предложения → графическая правка → проверки → approval → Git merge → воспроизводимый комплект».

**В составе:**

1. Approval **точного** Git head/tree, базовой ревизии `main`, pinned versions требований/правил и отчёта проверок. Коммит, статус контроля, human approval и merge не смешиваются.
2. Проверка fresh head/main и конфликтов, итоговый gate по обязательным формальным проверкам и ручным подтверждениям. Merge выполняет **уполномоченный человек средствами Git**; приложение проверяет результат ancestry/tree/hash и регистрирует его, но ИИ не делает merge.
3. Конфликты общего объекта или обновление `main` вызывают повторную проверку/согласование. Rollback — новый commit, без переписывания истории.
4. **Полный Diff требований** между immutable версиями BRD (добавлено/изменено/удалено), подтверждение неоднозначного сопоставления архитектором, выборочная инвалидация только затронутых approvals/зависимостей. Это отдельный механизм от Git/model diff PR 5.
5. Выгрузка A-01–A-07, JSON и двух видов `.puml`/SVG из одной точной редакции; draft exports маркируются, согласованные — связаны с версией и источниками.
6. Recovery/backup/restore PostgreSQL, Git, файловых версий и checkpoint; тест повторной операции, аварийного разрыва между SQL/Git и восстановления истории.
7. Воспроизводимое оценивание на заранее размеченном синтетическом наборе: Faithfulness, Citation Faithfulness, полнота требований/объектов/связей, необоснованные предложения, полнота formal/semantic defects и доля ложных замечаний. Сохраняются числитель, знаменатель, состав датасета и версия модели. Числовые цели semantic quality определяются после экспериментов.
8. Финальный Playwright happy path и обязательные negative paths на настоящих PostgreSQL/Git, отдельное LLM smoke/evaluation выбранной локальной модели. Документировать известные ограничения, настройку/локальную установку и границы безопасности.

**Наблюдаемая приёмка:**

- [ ] Созданы два задания от конкретной `main`, внесены и рассмотрены изменения общего объекта, показана история и различие между применением/commit/approval/merge.
- [ ] Неустранённое формальное нарушение, непроверенное обязательное правило или stale approval препятствуют финальному согласованию; промежуточные коммиты остаются возможными.
- [ ] При изменении main/concurrent revision согласование не переносится молча; конфликт требует вмешательства человека и нового проверки/approval.
- [ ] Diff двух BRD показывает добавления/удаления/изменения и инвалидацию **только зависимых** согласований, остальные сохраняются.
- [ ] Экспортированные A-01–A-07, `.puml`/SVG и JSON относятся к **одной** редакции и повторно строятся без LLM.
- [ ] Все AC-01–AC-20 проверены по матрице; частичные результаты из прежних PR доведены до конца либо ограничение явно зафиксировано без ложного `PASS`.
- [ ] Пройдены восстановление после сбоя и runtime проверки с реальными БД/Git; результаты оценки качества опубликованы с воспроизводимой разметкой/параметрами.

**Размер PR 9:** не создавать заранее десятый PR ради симметрии. Если работа окажется слишком велика, отдельно согласовать разбиение по независимо проверяемым границам, сохранив единый критерий финальной приёмки.

## 6. Тестовая стратегия и негативные сценарии

### Поэтапное накопление корпуса

- PR 1: fake LLM, streaming/cancel/reconnect/restart/error; отдельный локальный GPU smoke.
- PR 2: полный источник с подтверждаемыми локаторами, повреждённая версия, новый документ, недостоверная цитата, malformed structured output, prompt injection.
- PR 3: отдельный неполный документ, блокирующий и неблокирующий пробелы, принятое допущение, idempotent replay SQL.
- PR 4: структурные дефекты, неверный `expected_head`, повтор `operation_id`, crash между SQL и Git, разные task branches.
- PR 5: один объект на двух видах, изменение свойств, удаление только из вида, конкурирующий diff, открытые проверки.
- PR 6–7: корректный синтетический кейс отчётности плюс специально внесённые дефекты потоков, протоколов, направлений, исключений и защиты.
- PR 8: отдельное formal/judge сравнение, false positives, смена обязательного правила, ручное покрытие неформализованного требования.
- PR 9: непрерывный E2E, слияние и конфликт, BRD version diff, selective stale approval, backup/restore, полный A-01–A-07 и evaluation.

По BRD итоговый размеченный набор для AC-14/15 должен содержать **не менее 20 сценариев, 100 обязательных объектов и связей, 20 формальных и 20 смысловых дефектов, 20 корректных контрольных случаев**. Разметка подтверждается архитектором *до* оценки; числовые цели semantic quality нельзя объявлять выполненными до измерения. Отдельно фиксировать пропуски, ложные срабатывания, число необоснованных объектов и числители/знаменатели метрик.

### Общие правила проверок PR

- Каждая задача PR имеет TDD-набор «намеренно падающий тест → реализация → зелёная проверка», а не проверку текста сообщений об ошибке. Проверять тип результата, изменение состояния, инвариант и эффект для пользователя.
- Unit tests на Domain/Application; integration на настоящих PostgreSQL/Git/files/PlantUML при появлении соответствующего слоя; E2E Playwright на главных UI-сценариях.
- Типизация строго в `mypy`/TypeScript strict; `ruff` — единственный Python formatter. Не отключать проверки целыми пакетами и не скрывать ошибки чрезмерными подавлениями.
- В обычном CI LLM заменяется управляемым fake endpoint; **это проверка поведения приложения, не качества ИИ**. Тесты настоящих модели/сервера проводятся отдельно, с записью версии и конфигурации.
- Изменение contract или модели сопровождается тестом совместимости с уже принятыми сценариями; нельзя ради следующего PR незаметно ломать предыдущую пользовательскую возможность.
- Не считать «полный документ», «работает с моим примером» или «есть зелёный CI» достаточной проверкой всего MVP.

## 7. Workflow для Codex и критерий готовности PR

1. Начать новую ветку **от актуальной `main` приложения** (ветка `main` архитектурной модели относится к отдельному управляемому репозиторию).
2. Для конкретного этапа прочитать BRD/technical docs, изучить затронутый код и зафиксировать короткую спецификацию в `docs/superpowers/specs/`.
3. Применить Superpowers brainstorming для оставшихся проектных решений; согласовать их, затем `writing-plans`. План хранить в `docs/superpowers/plans/`, с точными путями, контрактами, тестами, ожидаемыми командами и небольшими коммитами. **Не превращать дорожную карту в реализацию девяти PR одновременно.**
4. Работать TDD маленькими проверяемыми блоками, без добавления архитектурного слоя «на будущее» без конкретного use case. При необходимости использовать отдельный Git worktree в локальном Codex.
5. Перед PR выполнить актуальные проверки (lint/types/unit/integration/E2E, по мере появления возможностей), проверить diff, выполнить независимое review и описать фактические проверки. Непроверенное явно указывать.
6. Открыть PR только после воспроизводимого результата. В PR перечислить реализованные/частичные FR/AC, отдельные негативные тесты, инструкции запуска, известные ограничения и что намеренно отложено.
7. **Merge только по решению человека.** После него актуализировать ветку следующего этапа; не держать девять долгоживущих веток с пересекающимися изменениями.

**Первым реализовать только PR 1.** Его детальную структуру модулей, HTTP/SSE contract, статусы и отмену, SQL schema/миграции, выбор локальной модели/vLLM-профиля, Docker/WSL2-команды и тестовые сценарии уточнить в отдельном Superpowers brainstorming/spec/plan. Не открывать PR 2 до завершения и проверки PR 1.
