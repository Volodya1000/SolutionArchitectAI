## Python: набор без дублирования

Планируется: Ruff для линтинга/форматирования, Pyright для типов, pytest для поведения и узко выбранный WPS231 для когнитивной сложности.
Все перечисленные ниже проверки — план будущих конфигураций; этот PR не добавляет runtime-зависимости или проверки ещё не созданного приложения; тесты и CI издателя документации обновляются отдельно.
Актуальность оценена по официальной документации на дату [исследования](README.md); разрешимость совместимых стабильных пакетов проверяется при создании lock-файла.
`latest`-документация может описывать development/preview: это не основание включать нестабильные правила или pin версии из заголовка сайта.

| Инструмент | Что даёт и с чем пересекается | Рекомендация |
| --- | --- | --- |
| [Ruff](https://docs.astral.sh/ruff/rules/) | Реализует множество проверок Flake8, Bandit и часть Pylint; не запускает эти плагины и не равен их полному покрытию | Основной линтер; один formatter `ruff format` |
| [Bandit](https://bandit.readthedocs.io/en/latest/) | Отдельный AST security-анализ с plugins; частично пересекается с Ruff S | Не включать полный параллельный запуск; при реализации Git/renderer сравнить актуальные B/S-каталоги и включить только обнаруженные полезные пробелы |
| [Pylint](https://pylint.readthedocs.io/en/stable/) | Inference, межмодульные проверки и design-диагностика; часть правил уже есть в Ruff PL и проверке типов | Полный второй линтер не добавлять; конкретный недостающий дефект может обосновать точечное включение |
| [wemake-python-styleguide](https://wemake-python-styleguide.readthedocs.io/en/latest/) | Flake8 plugin с архитектурными ограничениями и cognitive complexity; полный набор слишком предписывающий | Только WPS231, без всего WPS и без второго formatter |
| [Pyright](https://github.com/microsoft/pyright/blob/main/docs/configuration.md) | Статические типы, generics/Protocols, async, strict diagnostics | Один type checker; начать strict с domain/application, типизировать порты адаптеров |

Mypy — полноценная альтернатива Pyright с plugin-экосистемой; здесь Pyright удобен быстрым анализом Protocol/async и обратной связью IDE.
Не запускаем одновременно оба ради числа инструментов. `Any` внешнего SDK локализуется адаптером; ошибки схем проверяет runtime Pydantic.
AST-линтеры не подтверждают безопасность prompt execution; ограничение полномочий из [agents.md](agents.md) проверяется поведением.

Целевая версия проверок backend — Python 3.13. PyPI metadata на 12 ноября 2026 года допускают её для Ruff 0.17.4 (>=3.7), Pyright 1.1.414 (>=3.7), import-linter 2.16 (>=3.11) и pytest 9.2.0 (>=3.10). Ruff, import-linter и pytest явно указывают классификатор 3.13; Pyright настраивается на `pythonVersion = "3.13"`. Источники: [Ruff](https://pypi.org/pypi/ruff/json), [Pyright](https://pypi.org/pypi/pyright/json), [import-linter](https://pypi.org/pypi/import-linter/json), [pytest](https://pypi.org/pypi/pytest/json). Точечный WPS231 остаётся дополнительной dev-проверкой после проверки совместимости Flake8/WPS, а не обязательной runtime-зависимостью.

## Предлагаемый строгий профиль Ruff

Выбираем стабильные правила явно, а не `ALL`; точный список закрепляется и проверяется на каркасе.

| Категория | Планируемые правила | Польза |
| --- | --- | --- |
| Ошибки и неиспользуемый код | F, E4/E7/E9, B, UP, I | Неизвестные имена, импорты, опасные конструкции, современный синтаксис и порядок импортов |
| Надёжность | ASYNC, BLE, A, C4, SIM, PIE, RET, RUF, PGH | Async-ошибки, слишком широкие except, затенение builtins, избыточные конструкции и неконтролируемые suppressions |
| Предметные ошибки | DTZ, G, LOG, T20, ARG, PT | Часовые пояса, корректное логирование, отсутствие print в runtime, забытые параметры и понятные pytest-конструкции |
| Безопасность | S, с адресными обоснованными исключениями | Статические признаки небезопасных subprocess, сериализации, секретов и сетевых вызовов |
| Размер и цикломатическая сложность | C901, PLR0912, PLR0913, PLR0915 | Сложность ветвления, число веток/параметров/операторов |

Начальные рекомендации: C901 ≤ 10, число веток ≤ 12, параметров ≤ 6, операторов ≤ 50; это внутренние пороги ревью, не требование бизнес-предметной области.
Логическую читаемость проверяют также вложенность, состав булевых условий и разделение ответственности при ревью.
Ruff C901 измеряет McCabe, а PLR0912 — число веток: ни одно из них не является cognitive complexity.
Для неё рекомендуем Flake8 + wemake только с allowlist WPS231 и `max-cognitive-score=12`, согласно [описанию](https://wemake-python-styleguide.readthedocs.io/en/latest/pages/usage/violations/complexity.html) и [настройкам](https://wemake-python-styleguide.readthedocs.io/en/latest/pages/usage/configuration.html).
Flake8 в этом запуске не повторяет E/F/WPS-стили; WPS не является плагином Ruff. Дополнительный runner оправдан именно отсутствующей метрикой.
При внедрении проверяется поддерживаемый Python, совместимость Flake8/WPS и фактическое срабатывание WPS231; инструменты остаются только development-зависимостями.
Крупное булево выражение или неглубокая, но запутанная функция может пройти пороги: автоматические числа не заменяют человеческое ревью.

Docstring на каждый элемент, обязательные комментарии/копирайты и строгая форма имён ради формы не требуются: D/DOC/CPY не включаются автоматически.
Formatter-конфликтующие правила отступов/кавычек исключаются по документации Ruff, preview и unsafe auto-fix не запускаются автоматически.
В тестах разрешается S101 для assert; subprocess Git запускается списком аргументов без shell, исключение S603 при необходимости узко документируется в адаптере.
Не отключаем всю категорию безопасности для infrastructure или всех тестов; подавление содержит код правила и конкретную причину.
Статический анализ не находит весь мёртвый код: F/ARG ловят часть проблем, невызванные публичные функции требуют ревью, а не ложного обещания полного обнаружения.

## Тесты backend и критерии Хорикова

Изучен документ пользователя [maps/docs/test-and-solid-review.md](https://github.com/Volodya1000/maps/blob/4bc0d4b4a822b22c8f6e7ca1fbd8adbbe508a7dd/docs/test-and-solid-review.md), раздел «Критерии Владимира Хорикова».
Он связывает защиту от регрессий, устойчивость к рефакторингу, скорость обратной связи и сопровождаемость с наблюдаемым результатом, а не числом тестов.
Также учтены [правила организации тестов maps](https://github.com/Volodya1000/maps/blob/4bc0d4b4a822b22c8f6e7ca1fbd8adbbe508a7dd/docs/testing.md): линейный Arrange/Act/Assert и один понятный сценарий.
Принципы переносим на Python, а не копируем специфические проверки карты/Android.

| Принцип | Применение к SolutionArchitectAI |
| --- | --- |
| Защита от регрессий | Неверная ссылка не заменяет модель; смена HTTPS-правила снимает согласование; поздний proposal не стирает правку |
| Устойчивость к рефакторингу | Проверяем модель, доступный diff/отчёт и новый снимок, а не private-методы, DI-фабрики или порядок внутренних вызовов |
| Быстрая обратная связь | Чистые domain/use case тесты с маленькими синтетическими входами; реальный Git/JVM и LLM-evals идут отдельно |
| Сопровождаемость | Небольшие тесты с предметными именами, локальными fixtures, явными предусловиями и диагностикой |

Unit-тестируется поведение инварианта или use case, а не каждый метод класса. Перемещение логики между внутренними методами не должно ломать тест.
Fake допустим на внешней границе LLM/часов/ID; не подменяем валидаторы domain их ожидаемым ответом в проверке предметного правила.
Mock взаимодействия оправдан для внешнего контракта: например, запрет записи агентом или ограничение реальных сетевых попыток.
Точный счёт вызовов внутренних сервисов или формат внутреннего словаря не считается пользовательским контрактом.
Integration-тест хранилища использует настоящий временный Git, парсер и файловую систему; иначе не проверит сохранение после рестарта и ref-конфликт.
Unit может использовать fake repository для ветки конфликта, но это не доказательство атомарности реального Git-адаптера.

Предварительная организация тестов:

```text
backend/tests/
  unit/
    requirements/          # факты, вопросы, допущения
    architecture/          # модель и применение изменений
    verification/          # граф, правила, статусы
    agents/                # роли и переходы orchestrator
  integration/
    documents/             # источники, JSON/schema, локаторы ошибок
    history/               # Git, ref, сбои, восстановление
    llm/                   # SDK-адаптер без внешнего API
    http/                  # FastAPI, DI, ошибки/контракты
    rendering/             # настоящий PlantUML
  support/                 # builders, fake ports, небольшая синтетика
```

[pytest fixtures](https://docs.pytest.org/en/stable/how-to/fixtures.html) имеют минимально необходимый scope; изменяемый проект/temp directory отдельный для каждого теста.
Общий conftest содержит только общие механизмы; предметные fixtures живут рядом с фичей. Cleanup не скрывает утечки файлов/процессов.
Async-сценарии выполняются pytest с AnyIO; HTTPX ASGI transport подходит для HTTP integration, отдельный smoke проверяет настоящий сервер.
Ожидания ограничены timeout, без произвольных sleep; время и ID можно задавать fake-источником, но проверяем итоговый смысл.

## Обязательные сценарии и связь с BRD

| Набор | Проверяемый результат |
| --- | --- |
| FR-06, AC-11 | Неверный JSON/duplicate key, неизвестная schema version и неверная ссылка через JSON/UI/LLM сохраняют последнюю корректную модель; есть место и причина ошибки |
| FR-07, AC-12 | Black hole, miracle, изоляция, неверный тип/отношение и недостижимый поток обнаружены; законные источники/хранилища/получатели не дают ложных блокировок |
| FR-02, AC-10 | Допущение создаёт обе связанные записи A-01/A-07; ответ обновляет обе; конфликт обязательного стандарта нельзя скрыть допущением |
| FR-09–FR-10, AC-09/13 | Формальная ошибка не отменяется judge; «не проверено» не равно «пройдено»; смена правила HTTP→HTTPS блокирует повторное утверждение |
| Формализация правил | Привязка к валидатору проверяет типы параметров и применимость; неизвестный вид/неподтверждённая формализация не исполняются и не объявляются успешной проверкой |
| FR-11, AC-17 | Применение коммитит в task branch; approval ссылается на точный hash/tree; merge разрешён только человеку; Git failure, crash до/после ref update и повтор ответа не дают ложного успеха/двойной записи |
| Изменения и восстановление | Устаревший proposal конфликтует; восстановление сохраняет историю и требует актуальных проверок; подтверждённое решение не исчезает при новой генерации |
| FR-08, AC-16 | Из принятой модели формируются A-01–A-07, .puml/SVG; повтор без LLM сохраняет объекты, связи, классификацию и направления |
| Отрицательные примеры | Все строки [verification-scenarios.md](../verification-scenarios.md): SLA/хранение/диапазон, SEC-05–SEC-08, история Git |

SEC-05–SEC-08 проверяются как правила модели проектируемой системы, без реализации корпоративного 2FA, прокси или доставки отчёта в самом помощнике.
Отдельно integration проверяет приоритеты настроек/маскирование, lifecycle Dishka и ошибки рендеринга; unit не должен доказывать работу библиотек их подменами.
Сравнение эталона смысловое: выделенные системы/потоки/основания, а не дословная строка LLM и пиксельные координаты SVG.
Coverage помогает искать непроверенные ветви, но ни процент, ни количество тестов не заменяют покрытие критичных сценариев.
Прицельные мутации правила/ссылки полезны для оценки чувствительности теста; полный mutation testing не обязателен в каждом PR.

## LLM без обязательного внешнего API

Обычный CI использует fake LLM-порт с валидными/невалидными JSON, отказом, обрезкой, timeout, 429 и поздним ответом.
Integration адаптера `ChatOpenAI`/`StructuredOutputGenerator` использует локальный OpenAI-совместимый HTTP-stub для сетевых ошибок, capability mismatch и проверки числа попыток.
Внешняя сеть по умолчанию запрещена тестовой политикой; отсутствие ключа не превращает обязательный тест в молчаливый skip.
Тесты prompt builder проверяют наличие обязательных источников/решений и соблюдение бюджета, а не полную строку инструкций.
Fake judge проверяет формат/переходы, но не доказывает смысловое качество модели.

Реальные модели проверяются отдельным явно запускаемым eval с лимитами токенов/времени и зафиксированной синтетикой.
По AC-14/AC-15 набор до испытаний размечается архитектором: ≥20 сценариев, ≥100 обязательных объектов/связей, ≥20 формальных и ≥20 смысловых дефектов, ≥20 корректных контролей.
Фиксируются редакция набора/источников, модели, инструкции, параметры, результаты, числители и знаменатели; соответствие замечания дефекту проверяет человек.
Все внесённые формальные дефекты обязаны выявляться детерминированно; законные случаи не дают блокировок, нарушение всегда блокирует согласование.
Полнота генерации, доля элементов с основанием, число необоснованных предложений, полнота диагностики и доля ложных замечаний измеряются раздельно для формального и смыслового этапа.
При нулевом знаменателе показатель не объявляется успешным. Числовые цели LLM-генерации/смыслового ревью остаются открытыми до экспериментов.
Ручной пример — часть набора, а не доказательство качества будущего продукта; результаты fake-тестов не выдаются за результаты этих evals.

## Frontend

Выбранный стек — shadcn/ui + Tailwind CSS, assistant-ui и React Flow; [основания](frontend-library-evaluation.md). Линтеры, форматирование, проверка типов и тестовые фреймворки выполняют разные задачи.

| Проверка | Выбор и обоснование |
| --- | --- |
| Линтер | ESLint flat config, typescript-eslint recommendedTypeChecked, React Hooks и jsx-a11y: типовые async, hooks и accessibility ошибки |
| Formatter | Prettier отдельно; eslint-config-prettier отключает конфликтующие stylistic rules, см. [руководство](https://prettier.io/docs/integrating-with-linters) |
| Типы | TypeScript strict и `tsc --noEmit` отдельной проверкой: Vite build не заменяет typecheck |
| Unit/component | [Vitest](https://vitest.dev/guide/) + React Testing Library/user-event; jsdom для DOM-сценариев, MSW на границе HTTP |
| E2E | Playwright для небольшого набора сквозных сценариев frontend↔backend↔Git с fake LLM; Cypress — альтернатива без явного преимущества здесь |

[Typed linting](https://typescript-eslint.io/getting-started/typed-linting/) дополняет компилятор; не запускаем все строгие stylistic rules сразу.
Component-тесты проверяют доступные роли, ввод, ошибку/повтор, dirty-state при обновлении и конфликт версии; не проверяют внутренние hooks/структуру state.
Это соответствует [принципам Testing Library](https://testing-library.com/docs/guiding-principles/).
E2E нужны, потому что одни component-тесты не проверят сохранение Git, скачивание артефакта и UI после рестарта.
Начальный набор: импорт → предложение → правка → применение → согласование; невалидный кандидат JSON; stale proposal; восстановление; просмотр двух диаграмм и скачивание .puml/SVG.
Добавляются клавиатурная навигация и адаптивный smoke; автоматический axe-анализ дополняет ручную проверку focus/screen reader.
Playwright использует [наблюдаемое поведение и auto-waiting](https://playwright.dev/docs/best-practices), без нестабильных CSS-классов, sleep и snapshot всей страницы ради отчёта.

## Правила и будущий CI

Небольшие файлы ориентировочно до 200 строк — повод для обсуждения SRP, а не жёсткий gate искусственного дробления.
SOLID применяется к реальным границам, KISS/YAGNI ограничивают число абстракций, DRY не превращает похожие, но разные правила в одну сложную функцию.
Понятные имена, явные ошибки, минимум глобального изменяемого состояния; комментарии объясняют причину, не пересказывают код.

| Когда | Будущие проверки |
| --- | --- |
| Каждый PR с документацией | Относительные ссылки, scope diff и Markdown; существующая PDF-сборка сохраняется |
| Каждый PR с backend | Locked install, Ruff check/format check, Pyright, import-linter, WPS231, unit и локальные integration без внешних LLM |
| Каждый PR с frontend | Locked install, ESLint, Prettier check, tsc, Vitest, production build |
| При сквозных изменениях | Короткий Playwright-набор с реальным backend/Git и fake LLM; артефакты ошибок |
| При появлении контейнеров | Compose config/build, readiness и smoke с persistent volume; восстановление после рестарта |
| При изменении инструкций/моделей | Отдельный запуск синтетических eval, comparison отчётов; без обязательного реального LLM-вызова каждого PR |

Обновления зависимостей проходят те же проверки, проверку известных уязвимостей lock-файлов и ревью изменений API; новый линтер добавляется только ради конкретного пробела.
Правила import-linter ниже включаются в CI сразу после появления соответствующих пакетов; без фиктивных missing-module исключений.

## Архитектурные импорты

[import-linter](https://import-linter.readthedocs.io/en/stable/contract_types/) дополняет Ruff/Pyright: проверяет граф импортов, а не форматирование/типы. Выбираем отдельный `backend/.importlinter`, команда CI `lint-imports --config backend/.importlinter` из корня с установленным backend package. Конфиг появится вместе с пакетами, здесь — проект проверок.

| Contract | Конкретное ограничение |
| --- | --- |
| Layers | `di` → `presentation | infrastructure | persistence | config` → `application` → `domain`; порядок сверху вниз. Pipe означает независимые siblings, не последовательную зависимость адаптеров |
| Forbidden imports | domain запрещены application/adapters/presentation/config/di и внешние sqlalchemy, fastapi, langchain_core, langchain_openai, langgraph, dishka; application запрещены реализации/SDK/config/di |
| Independence | presentation, infrastructure, persistence независимы; не применять ко всем фичам без различия, если между ними есть законные application-контракты |
| Acyclic siblings | Для внутренних feature-пакетов domain/application — запрет циклов при разрешённых однонаправленных зависимостях; на выбранной версии проверить поддержку соответствующего contract |

Минимальный пример синтаксиса layers (фрагмент будущего файла, не установленная проверка):

```ini
[importlinter]
root_package = solution_architect_ai
include_external_packages = True

[importlinter:contract:layers]
name = Application boundaries
type = layers
layers =
    solution_architect_ai.di
    solution_architect_ai.presentation | solution_architect_ai.infrastructure | solution_architect_ai.persistence | solution_architect_ai.config
    solution_architect_ai.application
    solution_architect_ai.domain
```

[Layers](https://import-linter.readthedocs.io/en/stable/contract_types/layers/) запрещает обратные и косвенные зависимости, но разрешает верхнему слою импортировать любой нижний: отдельно [forbidden](https://import-linter.readthedocs.io/en/stable/contract_types/forbidden/) запрещает application/domain внешние SDK (с include_external_packages=True) и инфраструктурные пакеты. Для списка внешних пакетов указываются реальные import names, не distribution names. [Independence](https://import-linter.readthedocs.io/en/stable/contract_types/independence/) выражает peer isolation; не смешиваем pipe и colon на одной строке. DI исключается из peer independence и законно импортирует реализации.

Нет blanket ignore_imports. Composition/bootstrap не реэкспортируется из корневого __init__, иначе косвенная связь создаст ложные циклы; TYPE_CHECKING imports не используются для обхода границ. Конфигурация проверяется на разрешённом примере и на искусственном forbidden import, а не только зелёным запуском пустого пакета. Acyclic contract/ручное ревью также нужны внутри слоя: один layers contract сам по себе не запрещает все циклы одного пакета.

## Async, хранилища и контрактные испытания

- Отмена до LLM, во время streaming/backoff, после CAS Git и при shutdown; поздний ответ не применяет proposal, HTTP disconnect не дублирует commit.
- Отдельная AsyncSession на конкурентную задачу; pool/clients/subprocess закрываются; TaskGroup не оставляет фоновые задачи и thread callbacks после lifespan.
- Два применения с expected_head: один успех и один конфликт; повтор operation_id возвращает старый результат даже после продвижения HEAD, другой payload с тем же ключом отклоняется.
- Реальные PostgreSQL + временный Git + local storage: fault injection на каждом шаге journal, включая S3 upload до DB pin и CAS до SQL completed. Для S3 — тот же FileStorage contract suite с immutable versions и отказом удаления pinned source.
- Разрешённое обновление task branch после смены main, семантический конфликт общего объекта даже при чистом Git merge; checks/approval инвалидируются, фактический merge tree/родители сверяются с разрешением.
- Один объект на двух видах, отдельный layout/label override; удаление из вида не удаляет каталог. Round-trip/детерминированный JSON, неизвестная версия, broken refs и схема миграции.
- LangChain local HTTP stub: пустой/обрезанный/refusal, невалидный JSON и Pydantic, повторная генерация, неподдерживаемая JSON Schema capability, запрет скрытого Tool Calling, общий лимит сетевых и validation retries, retries=0, deadline/cancel. Один и тот же агентный контракт для двух endpoint profiles; реальная LM Studio/vLLM совместимость проверяется отдельным smoke, не выводится из stub.
- Clarification resume после restart, повтор ответа и повторное формирование вопросов не создают дублей; ContextBuilder учитывает closed questions, обязательные источники, budget и revision invalidation.

## Метрики качества ИИ

| Метрика | Что измеряем и где предел |
| --- | --- |
| Faithfulness | Поддержаны ли утверждения переданными источниками; не доказательство правильности решения |
| Citation Faithfulness | Подтверждает ли конкретная ссылка соответствующее утверждение; отдельно проверяем version/locator |
| Полнота генерации | Найденные обязательные объекты/связи к размеченному эталону |
| Корректность объектов/связей | Типы, семантика, направления и согласованность с требованиями, отдельно от синтаксиса JSON |
| Полнота выявления нарушений | Найденные дефекты к внесённым, отдельно formal/semantic |
| Доля ложных замечаний | Необоснованные замечания к выданным; нулевой знаменатель — N/A |
| Необоснованные предложения | Абсолютное число и доля без проверяемого основания, особенно против решений человека |

Retrieval coverage/recall и пропуски обязательных источников измеряются отдельно: высокая Faithfulness не исправляет исключённый из контекста запрет. У всех метрик фиксируются определение, набор/разметка, numerator/denominator, prompt/model/backend version и параметры. Нет вымышленных порогов согласованного смыслового качества. Человек подтверждает разметку и решения; формальные валидаторы не подменяются LLM judge.

Frontend tests добавляют Light/Dark/System + reload/system change, контраст SVG/Markdown/diff, длинные русские таблицы, дерево/where-used и клавиатуру; stream cancel/reconnect/multi-chat не перемешивают сообщения. PDF-сборка документации не доказательство работы продукта.

## Дополнительные критерии корректировки архитектуры

В последующих PR разработки обязательны lifecycle-тесты фабрик/scope (успех, исключение, отмена, частичная инициализация), запрет создания ресурсных реализаций вне providers, отдельная session для concurrent tasks. Приоритеты единого Settings проверяются в development/test/production, включая вложенный env override поверх YAML и redaction ошибок.

LangGraph проверяется на interrupt/ответ/resume после перезапуска, повторный запуск узла, конкурентные независимые операции и освобождение AsyncPostgresSaver после отмены. Application/Domain отдельно проверяют частичный пересчёт по версиям входов, stale Git revision, конфликт параллельных результатов и отсутствие повторного применения предметного изменения. Domain-тесты проверяют допустимые операции/инварианты и round-trip независимого сериализатора. Проверки документарного JSON-примера в зависимом PR относятся только к сохранённому эталону и не подтверждают реализацию Domain.

Для React Flow проверяются независимые layout двух видов, предметные ID, создание/изменение связи и семантический diff с принятием/отклонением; JSON графа не попадает в предметную сериализацию. Для локального PlantUML — запрет URL/file includes, обходов через препроцессор и SVG active content, ограничения размера/времени/параллелизма, кириллица и поддерживаемый профиль ArchiMate. Для будущего OpenShift — arbitrary UID, доступ к durable data, readiness и отдельный шаг миграций, без обещания испытанного production.
